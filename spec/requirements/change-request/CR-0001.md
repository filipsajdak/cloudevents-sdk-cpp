# CR-0001: An invalid CloudEvent must not be representable

## What prompted this

A hardening audit of the SDK, run against the v0.3.0 tree on 2026-09-21, looking for
memory safety, const-correctness, misuse resistance and resource use.

The audit found no memory-safety defect in the event model. What it found is that the
model places no obstacle in front of a caller who builds an event the CloudEvents
specification forbids, and that the only thing standing between such an event and the
wire is a defensive re-validation that the encode paths happen to perform.

## The present design

`docs/SPEC.md` section 9, decision D1, settles on a public aggregate:

> `event` as public aggregate vs builder with private state -> Aggregate; `validate()` is
> the gate

`include/cloudevents/core.hpp` implements exactly that. Every context attribute is a
public, mutable member. `validate()` is a separate const member the caller may or may not
call.

Consequences the audit observed in the tree as it stands:

1. `ce::event e{.id = "", .source = "", .type = ""};` is well formed and compiles. It
   violates CloudEvents v1.0.2 core section 3.1 three times over.
2. An event that passed `validate()` can be invalidated afterwards by assigning to a
   public member, and nothing re-checks it.
3. `validate()` is not `[[nodiscard]]`-protected by the type system in the sense that
   matters: a caller can simply not call it. Nothing in a signature says it must be.
4. Two of the four encode paths call `validate()` defensively and two do not, so whether
   an invalid event reaches the wire depends on which entry point the caller chose.
5. `uri` and `uri_ref` convert implicitly from `std::string` and from `const char*`, so a
   string silently becomes either of two semantically different CloudEvents types, and the
   `const char*` overload is undefined behaviour for a null pointer.
6. Four fallible mutators are missing `[[nodiscard]]`, so a rejected `set_extension` is
   silently discardable.

None of these is a bug in the sense that a test would catch it. They are the same
observation from six directions: validity is a property the caller is trusted to maintain,
rather than a property the type guarantees.

## What is requested

Move validity into the type system, so that the compiler and the constructors enforce what
`validate()` currently asks the caller to remember.

Specifically:

- Each context attribute becomes a type that cannot hold a value the specification
  forbids. Construction is a fallible factory for runtime text, and a `consteval` path for
  a literal, so a hardcoded `source` or `type` is checked when the program is compiled and
  costs nothing when it runs.
- `event` is constructed only from those types, or through a builder for decoders that
  discover attributes one at a time. It carries no public members.
- The headers a binding produces gain the invariant that at most one field carries any
  given `ce-` attribute, while the type a transport hands the SDK stays permissive,
  because a transport can hand it anything.

## What this costs

This reverses a settled decision, so it is stated plainly rather than framed as a
refinement.

- **It is a breaking API change.** Every call site that builds an event with a designated
  initializer stops compiling. The project is pre-1.0 and `docs/SPEC.md` section 3
  contemplates exactly this kind of change before the version is fixed, but the cost is
  real and lands on every consumer.
  *Corrected by CR-0002: SPEC section 3 rule 4 has no pre-1.0 exception, so the new
  model ships as `ce::v2` and `ce::v1` keeps the v0.3.0 declarations.*
- **`validate()` is removed rather than kept as a stub.** Every rule it enforces is a
  single-attribute rule, and CloudEvents v1.0.2 core defines no constraint spanning two
  context attributes, so once each attribute is valid by construction there is nothing
  left for it to check. A member that always succeeds would be worse than its absence: it
  would read as a gate while gating nothing.
- **The aggregate's readability is lost.** A designated initializer naming eight
  attributes is genuinely pleasant to read, and a constructor taking three attribute
  literals plus an options aggregate is a little less so. D1 chose the aggregate for this reason and the reason was
  sound; it is outweighed, not refuted.

## Alternatives considered and declined

- **Keep the aggregate; make `validate()` mandatory by convention.** This is the status
  quo, and the audit's finding is that convention is not holding: two encode paths already
  forget it.
- **Keep the aggregate; have every encode path validate.** This closes item 4 and nothing
  else. An invalid event still exists, is still passed around, and is still refused late
  and far from where it was built.
- **Strong attribute types, aggregate retained.** Attractive, and it closes items 1, 5 and
  6. It does not close item 2: the members stay public and assignable. It was declined
  because it pays most of the migration cost for part of the benefit.

## Acceptance

- No sequence of public API calls produces an `event` that CloudEvents v1.0.2 core
  section 3.1 forbids.
- An invalid attribute literal is a compile error naming the rule it broke.
- The wire output is unchanged: `test/fixtures/interop/` and
  `test/fixtures/conformance/` compare equal before and after, except where a
  tightening recorded in its own requirement deliberately changes what is accepted.
- The three specification gates stay green at every commit.
