# CR-0002: The v0.4.0 API is `ce::v2`, and `ce::v1` keeps what v0.3.0 published

## What prompted this

Preparing the v0.4.0 release, the checklist in `docs/RELEASE.md` opens with a rule the
work since v0.3.0 had broken:

> The API was fixed at `v0.1.0`: `SWR-BUILD-0006` requires a new version namespace for
> any breaking change after it.

`docs/SPEC.md` section 3 rule 4 says the same without conditions: "Inline namespace
`ce::v1`. Breaking changes go to `v2`, never mutate `v1`."

CR-0001 justified its breaking change by saying that SPEC section 3 "contemplates exactly
this kind of change before the version is fixed". It does not. Rule 4 has no pre-1.0
exception, and `RELEASE.md` records the version as fixed at v0.1.0. That sentence in
CR-0001 is wrong, and this request corrects it.

## What changed in `ce::v1` since v0.3.0

Measured by diffing the v0.3.0 headers against `main` with comments removed:

- The event model: `event` became a class, `validate()` is gone, and the extension
  accessors changed signature.
- `timestamp::fractional_digits` changed from `std::uint8_t` to `fraction_digits`, so
  `attribute_value` changed with it.
- `headers` became `raw_headers` plus a new, stricter `headers`, so `message` changed too.
- Everything that takes or returns an `event`: the binding core, the three bindings,
  `json_format`, `set_data` and `event_of`.
- The describe seam: `ce::name::value` became a `std::array`, and `for_each_field` takes
  its visitor by `const F&` instead of `F&&`.

Unchanged, or changed only by addition: `errc`, `error` and `result` (plus the new
`static_error` and `fail` overloads), the `json_codec` concept, the three codecs, and the
`CE_DESCRIBE` macro.

## What is requested

Honour rule 4 as written.

- The v0.4.0 API is declared in `ce::inline v2`.
- `ce::v1`, no longer inline, keeps every entity v0.3.0 published, with its v0.3.0
  declaration.
- An entity that did not change is declared once, in `ce::v1`, and `ce::v2` brings it in
  with a using-declaration. The describe seam goes back to its v0.3.0 declarations, so it
  can be one of these.
- `ce::v1` gets every defect fix that keeps its declarations: the timestamp renderer
  guard, base64 padding, the duplicate-field refusal and the `ce-datacontenttype`
  diagnostic. The RapidJSON and polyfill fixes are already in shared code.
- The v0.3.0 suites, examples and fuzzers come back, pointed at `ce::v1`, and run beside
  the v2 suites.

## What this costs

- **Two event models are maintained.** `ce::v1` adds back the v0.3.0 event model, format and
  bindings, and the 10,840 lines of v0.3.0 tests, examples and fuzzers. CI runs both
  generations.
- **Unqualified names now mean v2.** `ce::event` names the v2 class. A v0.3.0 consumer that
  spelled `ce::v1::event` keeps compiling; one that spelled `ce::event` must migrate or
  pin `ce::v1`. That is the mechanism rule 4 depends on, and `SWR-BUILD-0006`'s suite
  already pinned it.
- **v1 fixes stop at its declarations.** A v1 `timestamp` can still be given a digit count
  above nine by hand; the renderer is guarded so it no longer divides by zero, but the
  type still admits the state.

## Alternatives considered and declined

- **Freeze `ce::v1` from v1.0.0 instead**, so 0.x releases may break it. Declined by the
  owner on 2026-09-23 in favour of the rule as written.
- **Rename the namespace to `v2` and drop `v1`.** Satisfies the first half of rule 4 and
  breaks the second, since `v1`'s declarations would not survive.
- **Keep only the v1 event model, without bindings or format.** A v1 event could then not
  be sent anywhere, which keeps the declarations and loses the point.

## Acceptance

- Every public entity of v0.3.0 is reachable as `ce::v1::X` with its v0.3.0 declaration.
- The v0.3.0 suites pass against `ce::v1` in every preset, alongside the v2 suites.
- `ce::X` names the v2 entity, and a shared entity is the same type through both spellings.
- The three specification gates stay green at every commit.
