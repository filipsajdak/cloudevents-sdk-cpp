# CR-0004: A `json_document` that moves, in a new `ce::v4` generation

## What prompted this

v0.5.0, the first tag of `ce::v3`, published `json_document` with copy operations only, and its guide said so: "There is no default constructor, and moving a document copies it, so every `json_document` holds a DOM."
Its suite pins the same behaviour: `"a document is never empty"` moves a document and expects the source to still dump the same JSON.

`main` has since added move operations (`SWR-CORE-0035`, `D-CORE-9`).
A moved-from document now reads as JSON null, `get<Codec>()` returns `nullptr` for every codec, and it equals only another moved-from document.
`D-CORE-9` argued that this is an addition under `docs/SPEC.md` section 3 rule 4, because no declaration changed.
A release candidate, v0.5.1, was prepared on that basis.

On 2026-09-28 the owner ruled otherwise and withdrew v0.5.1.
A program that compiled against v0.5.0 still compiles, but a program that reads a document after moving it now reads a different value, and the published documentation promised the old one.
A change to documented behaviour breaks the API as surely as a changed declaration, so rule 4 and `SWR-BUILD-0006` put it in a new namespace.
The owner decided that the new generation is `ce::inline v4`, and that everything since v0.5.0 ships together in it as v0.6.0.

A new generation is the only moment the API may lose or change what it published, so the owner also decided what else v4 changes while it is open.

## What is requested

Every item below is the owner's decision, taken on 2026-09-28 and 2026-09-29.

**1. The move is a v4 feature, and v3 goes back to v0.5.0.**
`ce::v4::json_document` has move construction and move assignment, and promises exactly the moved-from state `SWR-CORE-0035` states: `dump()` returns `null`, `get<Codec>()` returns `nullptr` for every codec, and the document equals only another moved-from document.
`ce::v3::json_document` declares copy operations only, as v0.5.0 did, so moving a v3 document copies it and the source keeps its DOM.

**2. v4 `set_data` keeps a JSON media type and refuses any other.**
In v3, `set_data<T, Codec>` sets `datacontenttype` to `application/json` whatever the event declared (`SWR-EXT-0011`).
In v4 it follows the rule `encode_as` already follows (`SWR-EXT-0010`, `D-JSON-9`):
an absent `datacontenttype` becomes `application/json`; a JSON media type, as `is_json_content_type` defines one (`SWR-CORE-0024`), is kept; any other media type is refused with `errc::type_mismatch`.
`set_data` therefore returns `result<void>`, and so do its `event_of` counterparts.

**3. v4 `json_format` drops seven helpers.**
`required_text`, `optional_text`, `read_required`, `read_optional`, `read_time`, `read_context_attributes` and `read_extensions` are public static members of v3's `json_format<Codec>`.
Nothing in the tree calls them, no suite tests them, and no requirement names them.
v4's `json_format` does not declare them.

**4. `message::body` stays `std::vector<std::byte>`.**
The owner asked for the cost of the body type to be measured before deciding; PR #69 measured it.
A body that owns a `std::string` would save at most 1.3 to 3.0 percent of instructions and one 506-byte allocation on `http_encode_structured`, and nothing on any binary-mode path.
The owner decided on 2026-09-29 that this does not justify changing the type of a member every binding and every caller touches.
`message` stays shared and unchanged; rvalue entry points such as `from_message(message&&)` may be added later, as additions.

**5. A JSON body received in binary mode becomes a document.**
In v3 the body reader of `SWR-BIND-0006` stores a binary-mode body whose media type is JSON as `json_text`, unparsed.
In v4, `from_message<Codec>` parses it with `Codec` and stores a `json_document`, under the same rules and with the same failures as structured decode:
it takes `json::decode_options`, with the same 16 KiB retention default (`SWR-JSON-0040`);
above the limit the payload is `json_text`;
a body that is not valid JSON under a JSON media type fails with `errc::parse_error`.

**6. The generations convert into each other.**
`ce::v4::from_v3(const ce::v3::event&)` and `ce::v4::from_v3(ce::v3::event&&)` return a `ce::v4::event`; `ce::v4::to_v3(const ce::v4::event&)` and `ce::v4::to_v3(ce::v4::event&&)` return a `ce::v3::event`.
They are infallible and return the event itself, not a `result`, because every v3 event is a valid v4 event and the reverse differs only in the moved-from state.
A payload held as a `json_document` converts in constant time: the document model is declared once, in `ce::v3::detail`, and both generations' documents point at it, so a conversion copies or moves one `std::shared_ptr` and never a DOM.

**7. The layout follows the v2 precedent.**
The v0.5.0 headers that mention `event`, `data_t` or `json_document` are frozen as copies under `include/cloudevents/v3/`: `core.hpp`, `format/json_format.hpp`, `format/typed_payload.hpp`, `binding/common.hpp`, `binding/http.hpp`, `binding/kafka.hpp` and `binding/nats.hpp`.
An entity unchanged since v0.5.0 is declared once and brought into `ce::v4`.
The optional module exports `ce::v4` only.
The v0.5.0 suites are frozen under `test/v3/` and run against `ce::v3`, so its behaviour stays pinned as well as its declarations, as `SWR-BUILD-0011` and `SWR-BUILD-0012` do for v1 and v2.

ADR-0012 records how.

## What this costs

- **A fourth event model.** v3 joins v1 and v2 as a frozen generation, with seven headers under `include/cloudevents/v3/` and the v0.5.0 suites under `test/v3/`. CI runs four generations.
- **v3 keeps its copy on move.** A v3 user who wants the move migrates to v4; `ce::v3` stays as fast as v0.5.0 was, not faster.
- **v4 `set_data` can fail.** Code that called it as a statement must check the result. That is the migration, and it is why it waits for a generation.
- **Binary-mode receive parses the body.** In v3 a JSON body was stored unparsed, so a malformed one went unnoticed until someone read it. In v4 it is parsed on receive: it costs a parse, it fails early, and a typed read of it parses nothing more.
- **Conversions need access to each generation's document model.** Both documents grant it to one detail accessor; for `ce::v3` that is an addition, which rule 4 admits.
- **`D-CORE-9` and ADR-0010's amendment of 2026-09-27 no longer hold** where they call the move an addition. `D-CORE-9` is corrected by the stage that freezes v3; ADR-0010 points to ADR-0012.

## Alternatives considered and declined

- **Ship the move in a v0.5.1 patch release.**
  A patch release cannot change documented behaviour. Declined by the owner on 2026-09-28, and v0.5.1 was withdrawn.
- **Narrow rule 4 to declarations, so a behaviour change is an addition.**
  That is the reading `D-CORE-9` took. It would make the namespace promise nothing about what a program observes, which is the part a consumer relies on. Declined by the owner on 2026-09-28.
- **Revert the move and stay on v3.**
  Keeps the rule without a new generation, and gives up the saving `SWR-CORE-0035` measured: moves of events, which every decode and batch makes, would count references again. Declined by the owner in favour of a generation that also takes items 2, 3 and 5.
- **Change `message::body` to own a `std::string` in v4.**
  Measured in PR #69 at 1.3 to 3.0 percent of instructions and one allocation on `http_encode_structured`, nothing on binary paths. Declined by the owner on 2026-09-29 (item 4).
- **Keep the seven `json_format` helpers in v4.**
  They are public surface nothing uses or tests, and a generation's first tag is the only moment surface can go (`docs/RELEASE.md`). Declined by the owner.
- **Make the conversions return `result`.**
  No conversion can fail, so a `result` would make every caller handle an error that cannot occur. Declined by the owner.

## Open questions for the owner

Each has a proposal in the requirement or ADR named; none is decided by this request.

1. **What `to_v3` makes of a moved-from v4 document.** v3 has no moved-from state and no codec to build a null with. `SWR-CORE-0040`, in `draft`, proposes a v3 document sharing the static moved-from model. The alternatives are `json_text` holding `null`, or no payload.
2. **An empty binary-mode body under a JSON media type.** v3 reads it as no payload. `SWR-BIND-0008` proposes keeping that, by refusing only a non-empty body; the alternative is `parse_error`, since an empty body is not JSON.
3. **The text kept above the limit in binary mode.** `SWR-BIND-0007` proposes the body's bytes exactly as received, since the body is the payload (`SWR-HTTP-0009`). Structured decode trims surrounding whitespace (`SWR-JSON-0043`); the alternative is to trim here too.
4. **The other decoding entry points of the bindings.** Item 5 names `from_message`. `http::from_batch_message` and `nats::from_payload` also decode JSON with the default options and cannot be given a limit. Should they take `json::decode_options` in v4 as well?
5. **`event_of::with_data` returns `result<event_of>`** in v4, as a consequence of item 2. Confirm the shape.
6. **Where the conversions are declared.** ADR-0012 proposes a header of their own, so a v4-only translation unit does not compile the v3 event model; its name is open.
7. **Which JSON media types `set_data` keeps.** The requirements use `is_json_content_type` (`SWR-CORE-0024`), which `encode_as` applies and which accepts any type whose subtype is `json` or ends in `+json`, `text/json` included. `D-JSON-9`'s prose says "`application/json` or a `+json` suffix". Confirm the function is the rule, and `D-JSON-9`'s wording is corrected to match.

## Acceptance

- `ce::X` names the v4 entity, and every v0.5.0 entity is reachable as `ce::v3::X` with its v0.5.0 declaration.
- The v0.5.0 suites pass against `ce::v3` in every preset, alongside the v4, v2 and v1 suites.
- Moving a `ce::v3::json_document` leaves the source holding its DOM; moving a `ce::v4::json_document` leaves it in the `SWR-CORE-0035` state.
- `from_v3` and `to_v3` convert events carrying every `data_t` alternative, and a document converts without a copy, serialisation or parse of its DOM, as a counting codec shows.
- v4 `set_data` on an event declaring `text/plain` fails with `type_mismatch` and leaves the event unchanged.
- A binary-mode message carrying a JSON body yields a `json_document` within the retention limit, `json_text` above it, and `parse_error` for a body that is not JSON.
- The three specification gates stay green at every commit, and `check_references.py` reports no warning at the v0.6.0 tag.
