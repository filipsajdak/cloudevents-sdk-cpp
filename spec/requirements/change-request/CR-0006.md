# CR-0006: Which binding or format comes next, scoped by cost, maturity and fit

> **Status, 2026-10-21.** Proposed, nothing decided. The owner asked for a ranking of six candidates and one recommended bet, and for no requirements and no ADR drafts.
> This request writes down the ranking, the bet and the wording change that optional format targets would need, so that the owner can decide.
> Every ruling it leaves open is listed under "Open questions for the owner".

## What prompted this

`docs/SPEC.md` section 1 lists six things as out of scope and "design must not block them": the MQTT, AMQP and WebSocket bindings, and the Protobuf, Avro and XML formats.
v0.6.1 is tagged, and the post-v0.6.0 plan (CR-0005, the freeze diff, `delivered_in`, the Kafka interop) is delivered.
The next piece of scope has not been chosen.

The owner interviewed on 2026-10-21 and the answers shape this request (next section): nobody waits for any of the six, so demand cannot break the tie, and a new format may bring its own third-party dependency.
That second answer touches the sentence "`ce::core` has no third-party dependencies except CTRE" and the requirements built on it, so this request also says what exactly would change.

## Owner decisions (interview, 2026-10-21)

1. **No real consumer or customer waits for any candidate.** All six are scoped by cost, spec maturity and fit. No candidate is promoted by demand.
2. **A new format may ship as an optional target with its own third-party dependency**, like the JSON codecs: one `ce::format_*`-style target per format, built only on request, with the core staying CTRE-only. This needs a change request that amends the dependency-constraint wording for format targets; the wording is under "The dependency wording that would change".
3. **The deliverable is a ranking of the six and one recommended bet** with the five bet fields. No requirements and no ADR drafts for the recommended candidate: the owner chose "ranking plus one recommended bet" over "requirement skeletons".

## The candidates, in detail

### MQTT binding

- The binding covers MQTT 3.1.1 and 5.0 PUBLISH messages. **Binary mode is MQTT 5.0 only**: the Content Type property carries `datacontenttype`, and "CloudEvents attribute names MUST be used unchanged in each mapped User Property". There is **no name prefix**, and every value is the attribute's canonical string. **Structured mode** works on both versions; on 3.1.1 "the content mode is always structured and the message payload MUST use the JSON event format", with the media type implied. No batch mode. A receiver treats a message as structured when its Content Type starts with `application/cloudevents`, otherwise as binary.
- **The message shape:** a payload (bytes), a Content Type property (5.0), and a list of user properties, which are UTF-8 string pairs and may repeat. `ce::message` fits: the header multimap holds the pairs, and Content Type needs a reserved name, with `content-type` in the Kafka binding as the precedent.
- **A divergence to confirm, and the strongest finding of this research:** `protocol/mqtt_paho/v2/message.go` in sdk-go, as the fetch summary quoted it, declares `prefix = "ce-"`, reads a user property only when its key starts with that prefix, and decides binary mode by the presence of `ce-specversion` and not by the absence of a CloudEvents content type. If that is right, the only SDK that could serve as the offline peer disagrees with the v1.0.2 text on two rules, as sdk-go did for NATS in D-NATS-1 (sdk-go#1334). **Unverified**: no clone or run confirmed it.
- **Core fit, read from `include/cloudevents/binding/common.hpp`, not built:** with an empty `attribute_prefix` (the spec's rule), `carries_prefix` is true for every header, so the `content-type` header the binding would write is read back as an attribute named `content-type`, and any foreign user property becomes an extension. So the unprefixed rule needs a new optional trait (for example a reserved-name set), in the style of `content_type_is_attribute`. That is an addition. With the Go prefix `ce-` the traits fit as they stand, and the binding is then a third behaviour only if the SDK disagrees with the spec as well. MQTT 3.1.1 receive has no content type, so the core's rule "structured when a CloudEvents content type is present, else binary" would pick binary where the spec requires structured JSON: a new entry point under a new name, which is an addition. Whether sdk-go's paho client covers 3.1.1 at all is **unverified** (the `message.go` summary says nothing of 3.1.1).
- **Dependency:** none. **Interop:** Go only, and see the divergence above; the Java README lists no MQTT binding. STK-INTEROP-0001 asks for agreement with "the Go and Java" SDKs, so MQTT could meet it half.
- **Size S to M:** no dependency, no new parser, one fuzz target.

### AMQP 1.0 binding

- Binary mode: attributes go into `application-properties` as `cloudEvents:<name>`; `datacontenttype` goes into the AMQP `content-type` property; the data is the application-data section as bytes. Types: Boolean to boolean, Integer to long, String to string, Binary to binary, URI and URI-reference to string, Timestamp to the AMQP timestamp. Structured mode puts the event, formatted, in the application-data section with the format's media type. No batch mode.
- The fetch summary read the value rule as: values "MUST either be represented using the native AMQP types above or the canonical string form", a receiver "MUST be able to interpret both forms", and an implementation "MUST be strict for outgoing messages". **The exact text of that last rule decides the fit and was not read in full.**
- **Fit:** `message::header_fields` holds string pairs. If outgoing messages must use the native types, the string-valued header cannot express a timestamp or a binary value: either the adapter that builds the AMQP message does the typing (a documented duty, an addition) or the core gains a typed header value (a new member type, which touches the published `message` and is therefore a break, so a new generation by D-BUILD-4). Multiple data sections and an `amqp-value` body are not addressed by the text.
- **Dependency:** none. **Interop:** Go (`WriteMessage` into a caller-supplied `amqp.Message`) and Java through Proton; both are the best two-peer match among the bindings, offline use probable and **unverified**.
- **Size M to L**, and a possible break.

### WebSockets binding

- Structured mode only, with three subprotocols: `cloudevents.json` (text frames), `cloudevents.avro` and `cloudevents.proto` (binary frames). No batch. JSON support is mandatory. The client sends `Sec-WebSocket-Protocol` and the server picks one.
- **Two facts that disagree, left as they are:** the file is in the `v1.0.2` tree, and the README release column shows "-" for it. Its maturity is therefore **unverified**.
- **Fit:** nothing to map but a subprotocol name and a frame type, so the binding is a small API next to the JSON format and is half of its value only with Avro or Protobuf. Go has `protocol/ws/v2`; Java has none; offline use is **unverified**.
- **Size S**, and little to verify against.

### Protobuf format

- Media types `application/cloudevents+protobuf` and `application/cloudevents-batch+protobuf`. The `CloudEvent` message holds `map<string, CloudEventAttributeValue> attributes = 1` and a `oneof data` of `binary_data` (2), `text_data` (3) and `proto_data` (4, `google.protobuf.Any`). The attribute value is a `oneof` over the seven CloudEvents types, with Integer as `int32` and Timestamp as `google.protobuf.Timestamp`; the batch is `CloudEventBatch { repeated CloudEvent events = 1; }`. Proto3.
- **Fit with the event model:** the typed attribute map matches the typed attribute variant, so no type information is lost, unlike Avro. The core's structured path is hard-wired to `json_format<Codec>` (`encode_structured` and `decode_structured` in `common.hpp`), so a binding call that works with any format means new entry points under new names: an addition. The smaller slice is a format-only API, `bytes <-> event`, with the binding integration after it. How `proto_data` (an `Any`: a type URL and bytes) is held in the payload is **not settled** (open question).
- **Dependency choice, for the owner:** libprotobuf (BSD-3 license, **not re-verified here**) needs `protoc` and Abseil, is not header-only, and for C++ "disclaim[s] all cross-runtime support and require[s] an exact match between the generated code version and the runtime version at all times", with no ABI guarantee across any release (protobuf.dev, cross-version runtime guarantee). The other path is a hand-written codec for the one fixed schema (varint, length-delimited, one map, one `oneof`, `Timestamp`, `Any`), which has no dependency and would not need the wording change below, but it touches the spirit of the SPEC non-goal "a JSON parser of our own".
- **Interop:** the best of the formats: sdk-java ships `formats/protobuf` and sdk-go ships `binding/format/protobuf/v2`, so Go and Java can both produce and read the bytes with no broker. The Java module's `.proto` was copied from spec v1.0.1 (its README), so whether the two SDKs agree with the v1.0.2 file is part of the test below.
- **Security:** a new decoder of untrusted bytes: length prefixes against the buffer, varint overflow, the `int32` range, duplicate map keys, unknown fields, an `Any` whose bytes are opaque. One fuzz target.
- **Size M to L.**

### Avro format

- 180 lines at `v1.0.2`. A record `CloudEvent` in `io.cloudevents` whose `attribute` map holds a union of null, boolean, int, string and bytes, and whose `data` is a union of bytes, null, boolean, a JSON-like map, an array, double and string. Timestamp and both URI types map to **string**, and non-binary data is "translated into a representation of the JSON value".
- **Fit:** the mapping is lossy in the direction we care about. A decoded extension that arrived as a timestamp or a URI is an Avro string, so the typed event cannot tell a string from a URI or timestamp except by attribute name, and the data union folds integers, doubles and nesting into a JSON-shaped value. A round trip of our event model is not guaranteed by the format. The media type `application/cloudevents+avro` was **not** confirmed in the document by the fetch (it reported "not mentioned"), so the media type is **unverified**.
- **Interop:** no CloudEvents SDK peer found for this format. sdk-java README marks the Avro format "not supported" and offers `avro-compact`, a different working draft. Goldens could come only from the Avro library itself, which does not test the CloudEvents mapping.
- **Dependency:** Apache Avro C++ needs C++17, Boost 1.38 or later with four compiled libraries, and Python at build time (Avro 1.12.0 C++ documentation); the license (Apache-2.0) was **not re-verified here**. A hand-written codec for the fixed schema is possible.
- **Security:** zig-zag varints, block counts (an allocation size read from the input), a recursive union for data, so a depth limit.
- **Size L.**

### XML format

- **Not part of the pinned version.** It is `working-drafts/xml-format.md` on `main`, "Version 1.0.3-wip", "a working draft", and the `v1.0.2` `formats/` listing has no XML file. `docs/SPEC.md` pins `v1.0.2`, and CLAUDE.md workflow rule 5 says the CloudEvents text wins over this SPEC. The precedent D-NATS-1 followed a work-in-progress document over the tag, but there the tag held an older text of the same binding; for XML the tag holds nothing.
- Namespace `http://cloudevents.io/xmlformat/V1`, an `<event specversion>` element, one element per attribute with `xsi:type` designators, `<data>` as base64, string or inline XML (`xs:any`), `<batch>`, media types `application/cloudevents+xml` and `application/cloudevents-batch+xml`. No XSD exists (a request for one was closed for inactivity).
- **Interop:** sdk-java has a `formats/xml` module; its status and behaviour were **not read**. No Go module seen.
- **Dependency:** pugixml, MIT license, header-only through `PUGIXML_HEADER_ONLY`, no DTD use ("pugixml does not use information supplied in document type declaration for parsing"), a no-exceptions mode (pugixml manual). libxml2 or expat would carry their own entity settings.
- **Security:** the largest text surface of the six: entity expansion and DTDs, namespaces and prefixes, whitespace-preserving rules, and arbitrary XML nesting inside `data`.
- **Size L**, for a draft that may still change.

## How the sizes were estimated

From this repository's merged pull requests, additions and deletions: the Kafka binding [#24](https://github.com/filipsajdak/cloudevents-sdk-cpp/pull/24) 806 and 2 in 18 files; the NATS binding [#25](https://github.com/filipsajdak/cloudevents-sdk-cpp/pull/25) 334 and 2 in 12 files; NATS binary mode [#31](https://github.com/filipsajdak/cloudevents-sdk-cpp/pull/31) 422 and 38 in 14 files; the Kafka and NATS fuzz targets [#26](https://github.com/filipsajdak/cloudevents-sdk-cpp/pull/26) 191 and 13; the Kafka interop against sdk-go and sdk-java [#95](https://github.com/filipsajdak/cloudevents-sdk-cpp/pull/95) 2,767 and 5, mostly Go, Java and C++ harnesses and committed records.
A binding on the shared core therefore cost about 0.4k to 0.8k lines of code, tests and requirements per mode, plus a fuzz target of about 0.2k, plus an interop pull request of an order of magnitude more lines, which are generated or harness code.
**S** is one such binding with its interop and fuzz target and no core change; **M** is about twice that, or a core addition; **L** is a new third-party dependency or parser, a new type mapping, or a possible break.
The ratios between the candidates are judgement; the line counts of the earlier pull requests are the only measured inputs.

Work items for any candidate, as Kafka and NATS had them: requirements (system, software, one `delivered_in`), the code, the tests that cite the requirements, the interop records and verifiers (SWR-SEC-0008's pattern), a fuzz target, the guide and the changelog, and packaging (a vcpkg feature and a Conan option for a candidate with a dependency, SWR-ADOPT-0006 and SWR-ADOPT-0007).

## Fuzz and CI cost

`.github/workflows/fuzz.yml` lists 28 matrix entries: 7 targets for each of 4 generations. New code added as `ce::v4` additions, as CR-0005 did, needs **one new target and so one more job**, not four: 60 seconds on every pull request and 900 seconds nightly, plus a seed corpus. Whether a new candidate's code lands in `ce::v4` only is the owner's rule 4 reading, not decided here.
A candidate with a dependency also adds at least one CI configuration that builds with the dependency present, which no candidate without one needs (an estimate; the number of jobs is **unverified**).
`SWR-SEC-0001` says "the decode path of every protocol binding": a format decoder is not named in it, so it would need a word.

## Ranking

The criteria the owner set: cost, spec maturity and fit, with demand excluded. The author added a fourth because STK-INTEROP-0001 makes agreement with the other SDKs the repository's only external measure of correctness: **can the wire form be verified offline against both sdk-go and sdk-java**.

| rank | candidate | why |
|---|---|---|
| 1 | **Protobuf format** | In the pinned tag; both reference SDKs ship it, so the verification the repository relies on (SWR-SEC-0008's shape) is available in full and needs no broker; the typed model maps without loss; an addition on the core. Costs more than a binding (M to L) and brings the dependency question. |
| 2 | **MQTT binding** | In the pinned tag; no dependency; cheapest real candidate (S to M); an addition. Ranked below Protobuf because the only peer, sdk-go, appears to disagree with the spec on the name prefix and on mode detection (to confirm), and sdk-java has no MQTT binding, so interop is at best one SDK. **By cost alone MQTT is first.** |
| 3 | **AMQP 1.0 binding** | In the pinned tag; two peers; no dependency. The typed `application-properties` against string headers makes a core break possible, and a break costs a minor version and a new generation (D-BUILD-4). |
| 4 | **WebSockets binding** | Cheap (S) but the thinnest: a subprotocol and a frame type, no `release` link in the README, one SDK peer, and half of it is the formats ranked above. Better after Protobuf than before it. |
| 5 | **Avro format** | In the pinned tag, but a lossy mapping, no SDK peer for this format, and the heaviest dependency (compiled Boost) or a hand-written codec. |
| 6 | **XML format** | A working draft outside the pinned version, no XSD, one unread peer, and the widest text-parsing attack surface. |

## Recommended bet

**The Protobuf event format, first slice: a format-only API (`bytes <-> event`) and its verification against sdk-go and sdk-java. No binding integration, no packaging, no dependency decision in this slice.**

| field | |
|---|---|
| **Need, in the customer's words** | **There is none.** No customer or consumer has asked for it (owner, 2026-10-21). The sentence that follows is the author's hypothesis and not a quotation: "a C++ service on a Protobuf-encoded event stream reads and writes the same CloudEvents bytes as its Go and Java peers." |
| **Riskiest assumption** | That the v1.0.2 Protobuf wire form is a stable shared target and that this SDK's event model maps onto it without touching a published declaration: that sdk-go and sdk-java produce bytes that decode to the same event (the Java `.proto` is from v1.0.1), and that every attribute type and data kind, `proto_data` (`Any`) above all, has a representation that is an addition. |
| **Smallest test** | A spike of at most one working week, no library code merged: produce goldens offline with sdk-go and sdk-java for about ten events (every attribute type, each of `binary_data`, `text_data` and `proto_data`, an extension of each type, a batch of two), compare the two SDKs' bytes and decoded events, and write the list of cases that do not map onto `event` and `payload` as they are. A throwaway reader of the goldens, outside the library, measures the size of the hand-written path. |
| **Success signal** | Go and Java agree on every golden (byte-equal or decode-equal; any difference is written down as a finding, as D-NATS-1 did); the mapping list has no case that needs a change to a published declaration, and `proto_data` has a proposed representation that is an addition; the spike gives a measured line count that replaces the S/M/L guess. |
| **Stop or pivot signal** | The two SDKs disagree on a v1.0.2 MUST, or the mapping needs a break: pivot to the MQTT binding (with the prefix question settled first) or stop. |
| **Decision date** | **2026-11-11**, three weeks after 2026-10-21: persevere, pivot or stop, with the signals above. |

This bet is a recommendation; the owner decides which bet, if any, goes ahead. The ScudoAI Planner server (`planner`) failed to connect in the session that wrote this request, so the bet is recorded here and not in the Planner; it moves there once the server answers.

## The dependency wording that would change

The owner ruled on 2026-10-21 that a format may be an optional target with its own third-party dependency. Only a candidate that brings a dependency needs this (Protobuf through libprotobuf, Avro through Avro C++ or Boost, XML through an XML parser). A hand-written codec, a binding, and the whole of the recommended first slice with a hand-written reader do not.
**Proposed wording only; none of these files is edited by this request.**

| text | says today | what would change |
|---|---|---|
| `CLAUDE.md`, "Hard constraints" | "`ce::core` has **no third-party dependencies except CTRE**. nlohmann/json may only be included from the `ce::codec_nlohmann` target." | Keep the first sentence. Replace the second with: a third-party library may be included only from the one optional target named for it (`ce::codec_*` for a JSON codec, `ce::format_*` for a format); no header of `ce::core`, `ce::format_json` or a binding includes it; the target exists only when requested. |
| `docs/SPEC.md` section 4 | "All targets are header-only INTERFACE libraries." and a target graph with the JSON codecs only | Add the exception "except an optional format target that links a compiled library", a row per format target, and a `CE_FORMATS` list next to `CE_CODECS`. The exact switch is not decided here. |
| `docs/SPEC.md` section 1 | the out-of-scope list; the non-goal "a JSON parser of our own" | Move the chosen candidate to "delivered"; state whether the non-goal extends to a hand-written wire codec (open question 2). |
| `SWR-ADOPT-0001` | "Four header-only targets" with a downward direction | Name the format targets and allow a compiled one when the format is optional. |
| `SWR-ADOPT-0002` | "The core depends on no third-party library except CTRE"; its statement covers "core, format and binding targets" | Reword so that the statement covers the core, `ce::format_json` and the bindings, and treats an optional format target like a codec target. | `SWR-ADOPT-0005` | the package configuration reports `codec_nlohmann` as not found when nlohmann is absent | One package component per optional format, with the same rule: not found without error unless requested. |
| `SWR-ADOPT-0006` and `SWR-ADOPT-0007` | vcpkg and Conan carry CTRE and the codec libraries; the `boost_json` option already needs a compiled library | One feature or option per optional format; for libprotobuf, the `protoc` and runtime versions must match (protobuf.dev). |
| `SWR-BUILD-0002` | the `#error`-only conditional is allowed in a "codec header" | Say "a codec or format header". |
| `SWR-BUILD-0005` | lists the headers of the targets | The new headers; an addition under `SWR-BUILD-0006`. |

## Risks

- **A divergent peer.** sdk-go may not follow the v1.0.2 text for MQTT (and may not for any other candidate). The repository has a way to record that, as D-KAFKA-2 and D-NATS-1 did, but a candidate whose only peer disagrees has no external check of its spec reading.
- **Facts read through a summary.** Every claim about an SDK or a document came through a fetch summary; the decisions in this request that rest on one are marked, and a spike would read the sources.
- **A format with a runtime that does not travel.** libprotobuf's exact version match between `protoc` and the runtime makes a binary package of `ce::format_protobuf` depend on the consumer's protobuf, which a consumer who vendors another version cannot satisfy.
- **A hand-written decoder is also a parser of untrusted bytes** with a fuzz target and none of a library's field history.
- **A break found late.** AMQP, or any candidate whose mapping needs a published declaration to change, would cost a new generation and a minor version (D-BUILD-4). The spike of the recommended bet is built to find that before any library code exists.
- **The bet has no demand behind it.** If the decision date passes with no consumer, the signals above are the only evidence; stopping is a valid outcome.

## Open questions for the owner

These are not decided here.

1. **Which weight wins?** Cost alone ranks MQTT first; cost with offline verification against both reference SDKs ranks Protobuf first. Which does the owner want the ranking to mean, and is the bet the one recommended?
2. **Protobuf: libprotobuf or a hand-written wire codec?** The first adds a dependency and the wording change above; the second needs none but touches the non-goal "a JSON parser of our own". Is the non-goal extended to a wire codec for one fixed schema?
3. **If MQTT is chosen: the spec (unprefixed names, content-type as a property) or sdk-go (the `ce-` prefix, mode by `ce-specversion`), if the divergence is confirmed?** D-NATS-1 chose the specification over sdk-go.
4. **Is the dependency wording amended now, or only when a candidate with a dependency is approved?** This request proposes the wording and edits none of the files.
5. **Is XML considered at all** while it is a working draft outside the pinned version, given the SPEC rule that the pinned CloudEvents text is normative?
6. **How is `proto_data` held in the payload?** As raw bytes with the type URL kept beside it, as an opaque value, or refused. The spike would propose; the owner decides.
7. **Do the Rust, C#, Python or other SDKs count as peers** for verification? This research did not look at them (**unverified**), and STK-INTEROP-0001 names Go and Java first, with Rust and C# in its rationale.
