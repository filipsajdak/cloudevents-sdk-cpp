# CR-0007: A branch coverage gate, measured without exception edges

> **Status, 2026-10-26.** The owner approved this request and ruled all six questions in five decisions (items 1 to 5 of "Owner decisions"; item 4 answers both the function gate and the pin).
> `SWR-SEC-0007` is amended and the gate implemented by one pull request, which also takes the throw-excluded figure from a main-line-equivalent run of the `coverage floor` job before the floor is written.
> No question is open.

## What prompted this

`SWR-SEC-0007` gates **line** coverage at 90 percent, and the `coverage floor` CI job enforces it with `gcovr --fail-under-line`.
Nothing gates branches. `D-SEC-3` recorded the first measurement, 60.5 percent of branches, and it has stayed near that figure since: 60.9 percent on the commit before pull request #110.
A line that holds `if (!x) return fail(...)` counts as covered when only the passing arm runs, so a release can meet the line floor with every error return untested.
Pull request #110 raised branch coverage with tests only (no library line changed) and the owner chose to raise first and gate afterwards; this request is the gate.

## Measurements

All figures are from the `coverage floor` job (gcovr 7.0, gcov-13, GCC 13, `-O0 --coverage`), the measurement of record under `D-SEC-3` and `docs/RELEASE.md`.
A local macOS run cannot reproduce them: Apple's `gcov` cannot read GCC's `.gcda`.

### The key fact: most uncovered branches are exception edges

Of the 3188 uncovered branches before #110, **2269 were exception edges**.
The library throws nothing by rule (`CLAUDE.md`, "Hard constraints"), but allocating calls (`Codec::set`, `std::string{}`, `push_back`) are not `noexcept`, so the compiler gives each a throw edge that no test can take.
Excluding them removes 2274 branches and only 5 covered ones: the denominator falls from 8146 to 5872 and the covered count barely moves.
Another 146 were closing-brace and scope-exit lines (97) and defaulted `operator==` short-circuit arms (49).
So the default branch figure measures how many calls allocate, and the figure without throw edges measures how many decisions the tests present both outcomes for.

## Decision proposed

**Gate branch coverage, measured without exception edges, on all files the line gate already measures, with a named floor constant.**

1. **Metric.** Branch coverage with gcovr's `--exclude-throw-branches`. The default metric is still printed (the summary and the HTML report), but it is not gated: its denominator is dominated by edges that no test can take.
2. **The flags.** In the `coverage-report` command, beside `--fail-under-line ${CE_COVERAGE_FLOOR}`:
   `--exclude-throw-branches --fail-under-branch ${CE_COVERAGE_BRANCH_FLOOR}`.
   Both exist in gcovr 7.0. `--exclude-throw-branches` also changes the printed branch figure, so the summary line and the HTML report show the gated metric.
3. **Scope.** The same `--filter` and `--exclude` as the line gate (everything under `include/cloudevents/` except `detail/expected_polyfill.hpp`), that is v1 to v4 and the shared headers together. The owner ruled that the frozen generations are in (decision 2).
4. **The constant.** `CE_COVERAGE_BRANCH_FLOOR`, a CMake cache variable next to `CE_COVERAGE_FLOOR` in `test/CMakeLists.txt`, with the unit and the provenance in its comment. It is the only place the number lives; `docs/RELEASE.md` and `CONTRIBUTING.md` name the constant and not its value.
5. **Floor and ratchet.** Proposed rule: **floor = measured - 2 points, rounded down to a whole percent; the floor is raised in the same pull request that raises the measurement, never lowered to make a release go out.**
   The 2 points come from the observed drift between unrelated code changes (about 0.2 points) with room for a handful of new decisions in a pull request that adds code and its tests. With the 88.1 percent measured after #110 the rule gives **86**.
   The floor never rises above the last measured figure on `main`, and a pull request that lowers coverage below it fails.
6. **Validity.** The floor holds only for the pinned toolchain of the `coverage floor` job: gcovr 7.0 from the Ubuntu 24.04 package and `gcov-13`. A local run on another gcov or gcovr is a question about the toolchain, as `docs/RELEASE.md` already says for lines.
7. **Pairing.** The gate is paired with the mutation report of `SWR-BUILD-0014` (advisory) as the guard against assertion-free tests: coverage says a branch ran, the mutation report says whether any assertion noticed.

## Alternatives considered

| alternative | verdict | why |
|---|---|---|
| Gate the default metric | **Not proposed.** | 63.5 percent of which 2269 branches (before #110) are untakeable exception edges: a floor near 60 would not discriminate and would move when the allocation pattern of a function changes, not when a test is removed. |
| Report only, no gate | Possible; the cost is that nothing stops the figure sliding. | `SWR-SEC-0007` exists because "an untested branch" should be "visible in review"; a report no one is forced to read is what `D-SEC-3` argued against. This is the fallback if the owner doubts the pinned-tool risk below. |
| Raise first, then gate | **Chosen by the owner, and partly done.** | #110 added tests for 218 error-path branches with no library change; the gate follows the raise. The residual (701 branches without throw edges) is in "Residual" below. |
| Exclusion markers (`GCOVR_EXCL_BR_LINE`, `GCOVR_EXCL_BR_START`/`STOP`) instead of the flag | Not proposed as the main mechanism. | A marker per allocating call would put hundreds of comments into the headers and would hide a real error branch beside it on the same line. The flag is a single, global, reviewable choice. Markers remain right for the few defensive branches that cannot be reached (class 3 in #110). |
| Gate branch coverage per file | Not proposed. | A floor per file would need a table that rots; the total floor with the ratchet is simpler. Revisit if one file hides behind a high total. |

## Residual after the raise

After #110 there are 701 uncovered branches without throw edges (919 before). #110 sorted the original 3188 into compiler artefacts (2415), real untested error behaviour (class 2) and defensive branches that cannot be reached (class 3, listed there for exclusion or removal).
The gate does not require the residual to be removed. It requires that the measurement does not fall.

## Risks

- **Toolchain drift changes throw-edge detection.** `--exclude-throw-branches` decides from the compiler's exception-handling edges as gcov reports them. A different GCC, gcov or gcovr version can classify more or fewer edges as throw edges and move the figure by points without any change to the tests. The floor is valid only with gcovr 7.0 and gcov-13; this request proposes no other toolchain for the job.
  **How a toolchain bump re-baselines:** the pull request that changes the pinned compiler, `gcov-N` or the gcovr source (the apt package, or a pip pin) runs the job, records the new measurement in the same pull request (a `D-SEC` entry that states both figures), and sets the floor again by the rule above. The floor is never left as it was on a bump, and never lowered below the rule's result.
- **A noisy floor blocking unrelated pull requests.** Measured drift between changes is about 0.2 points on an unchanged tree (the job is deterministic) and a 2 point margin leaves ten times that. A pull request that adds code with no test for its branches can still fail, which is the gate's purpose. A pull request that fails the gate through toolchain noise is re-baselined by a pull request of its own, not by `--fail-under` overrides.
- **Gaming with assertion-free tests.** A test that runs both arms of a branch without checking anything meets the gate. The pairing with the `SWR-BUILD-0014` mutation report is the guard; this request does not make mutation a gate, as that requirement forbids it.
- **A floor that does not distinguish the generations.** If the frozen copies stay in scope, a drop in v4 can hide behind a gain in a frozen copy (they hold 62 percent of the branches). The owner accepted this risk (decisions 2 and 4).
- **The measured value is a side measurement.** The throw-excluded figure came from a one-off run on a branch, and this request could not reproduce it from the artifact. A floor is never written before a main-line run of the job has printed it.

### Proposed text of `SWR-SEC-0007` (to be applied by the implementing pull request, not by this one)

Title: `Line and branch coverage floors for core, format and binding`

`rationale` addition: a line can run with one arm of its decision never taken, so a line floor alone leaves an untested error return invisible. The branch floor counts decisions, with the exception edges of allocating calls excluded because the library throws nothing and no test can take them (`CR-0007`, `D-SEC-5`).

Statement:

> The SDK shall report line and branch coverage for its core, format and binding sources. Line coverage shall reach ninety percent, and branch coverage with the compiler's exception-handling edges excluded shall reach the floor `CE_COVERAGE_BRANCH_FLOOR`, before a release is tagged. Both shall be enforced by the exit code of the coverage report and not by reading its output. The branch floor is valid only for the pinned `gcovr` and `gcov` of the `coverage floor` CI job, and is raised in the pull request that raises the measurement.

### Verification of the new text

`SWR-SEC-0007` is verified today by `test:test/CMakeLists.txt::coverage-report`: the target exists and fails the build below the floor, and `check_references.py` resolves the name in that file. The same entry covers the branch floor if the same target carries the flags, so no new `verified_by` form is needed.
Two additions are proposed so that the gate is evidenced and not only configured:

- a CTest guard (label `guard`, in the style of `warning-scope-probe-must-not-compile`) that greps `test/CMakeLists.txt` for `--fail-under-branch ${CE_COVERAGE_BRANCH_FLOOR}` and `--exclude-throw-branches` in the `coverage-report` command, so that dropping either flag fails a test and not silently the gate;
- the CI evidence: the `coverage floor` job's pass on the implementing pull request, and a recorded run with the floor temporarily above the measurement showing the job fails with gcovr exit status 4 (the proof that the gate gates; recorded in the pull request, not committed).

## Owner decisions

Ruled by the owner on 2026-10-26. They answer the six questions this request asked.

1. **The floor is 86.** It is the measurement minus 2 points, rounded down: 88.1 percent measured with exception edges excluded gives 86. The implementing pull request first takes the figure from a run of the `coverage floor` job and stops for the owner if it is not near 88.1 percent. The 2 point margin stands.
2. **The gate covers everything together.** v1 to v4 and the shared headers are one metric over all headers, as the line floor works today. A separate figure for v4 and the shared headers, or for the frozen copies, is declined.
3. **The ratchet is by a person.** The floor is raised by a person, in the pull request that raises coverage by a whole point, in the same diff. There is no automation and no pull request comment on a drop. The floor is never lowered to let a release go out.
4. **No function-coverage gate.** Functions stay at 91.9 percent and unreported as a gate. gcovr 7.0 and `gcov-13` are **pinned** in the `coverage floor` job: the packages are named explicitly and a step fails with a clear message when the installed versions differ, so a runner image update cannot move the throw-edge detection silently.
5. **The unreachable defensive branches are left as they are.** `json_format.hpp` lines 131, 553, 608 and 633, `timestamp.hpp:153`, `attributes.hpp:443`, `codec/nlohmann.hpp:93`, `result.hpp:54` and `json_slice.hpp:139` get no exclusion marker and are not removed. Alternatives declined: exclusion markers (a comment per branch that would also hide a real error branch beside it on the same line) and removal (it changes frozen headers, and `v1` to `v3` may only be added to or fixed).
