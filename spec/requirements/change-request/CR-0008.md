# CR-0008: An MQTT binding in two slices, as an addition to `ce::v4`

> **Status, 2026-10-25.** Approved.
> The owner made four rulings on 2026-10-24 (items 1 to 4 of "Owner decisions"): MQTT is a go as a bet; it ships as an addition in `ce::v4`; binary mode follows the specification text by default with an opt-in for sdk-go's `ce-` prefix; and the work comes in two slices.
> On 2026-10-25 the owner approved the request with its stage plan and ruled the two questions that had kept it `proposed` (items 5 and 6): a foreign User Property in binary mode is ignored (`SWR-MQTT-0013`), and a User Property named `content-type` beside the Content Type property is refused with `invalid_argument` (`SWR-MQTT-0008`).
> The design (ADR-0014) is accepted.
> One question stays open and is not needed by either slice: whether MQTT gets a `from_message_moving` (open question 3). No requirement is written for it until the owner rules.
> The requirements stay `reviewed` with no `satisfied_by` or `verified_by`; each moves to `approved` in the slice that writes its suite (the precedent is CR-0004 and CR-0005).

## Rule 4 verdicts

v4 is frozen since v0.6.0, as are v3, v2 and v1: only additions and body-only fixes to published declarations (`docs/SPEC.md` section 3 rule 4, `SWR-BUILD-0006`).

| # | change | verdict | consequence |
|---|---|---|---|
| a | a new header `binding/mqtt.hpp` declaring `ce::inline v4::mqtt` and a new target `ce::binding_mqtt` | **An addition.** A new namespace in a new header, as `binding/kafka.hpp` was; `message.hpp`, `binding/common.hpp` and every declaration of `v1` to `v3` are untouched. `scripts/frozen_api_diff.py` (`SWR-BUILD-0015`) is the check. | v0.7.0 or a patch release, the owner's call at release time; no new generation |
| b | the opt-in as a defaulted trailing template parameter (`name_policy Names = unprefixed_names`) on the new entry points | **An addition**, by the owner's ruling 2 of 2026-10-24. The entry points are new, so no existing call can bind to a different overload. | no change to a published declaration |
| c | `cloudevents.cppm` exports `ce::v4::mqtt` | **An addition**: the module exports `ce::v4` only (`SWR-BUILD-0013`) | the export list grows by one namespace |
| d | a reserved-name trait in `binding/common.hpp` | **Not done.** The spike showed a 20-line filter in the binding is enough. It would be an addition too and can follow as a refactor (ADR-0014). | nothing changes in the core |

## What prompted this

CR-0006 (merged, pull request 108) ranked six candidates and recommended MQTT as the first bet by cost: no dependency, no new parser, one fuzz target.
It also named one finding to confirm: that sdk-go disagrees with the specification on the binary-mode name rule.
The spike (`docs/spikes/mqtt.md`, pull request 112) confirmed it by reading both sources and running sdk-go offline, and found that the disagreement is confined to binary mode.
On 2026-10-24 the owner read the spike and ruled the points under "Owner decisions".
This request writes them down, with the requirements of both slices in `reviewed` status and the stage plan.

## What the spike established, and what it did not

Verified (all from `docs/spikes/mqtt.md`; sdk-go file:line at `05f0f6812a369b6950568b0b28788cfb44cc3279`, 2026-10-20):

- The text requires attribute names "used unchanged" (`bindings/mqtt-protocol-binding.md:168-169`, a MUST) and shows no `ce-` anywhere; sdk-go writes `"ce-" + name` (`write_message.go:97`), reads only `ce-` keys (`message.go:20`, `:82-89`) and refuses `CE-specversion`.
- `datacontenttype` is the Content Type property in both (`:146-147`; `message.go:95-97`, `write_message.go:92`); both test the Content Type first for the mode (`:114-119`; `message.go:43`); the canonical string values agree.
- Structured mode agrees, so the 16 Go goldens (`interop/mqtt-spike/goldens/go/`) verify slice 1 in both directions today.
- MQTT 3.1.1 is always structured JSON and has no properties (`:55-56`, `:135-136`); sdk-go does not support it (sdk-go#1190).
- sdk-java has no MQTT binding (README row not supported; no `mqtt` path at `81d64ac`), so the interop evidence has one peer.
- A 165-line sketch against the real headers passed 226 checks on gcc 16.2 (C++20, C++23) and Apple clang (C++20) under `-Werror`, including every Go golden in both name rules.

Not verified, and not claimed:

- The MQTT packet bytes (the evidence is the paho `Publish` struct, not the wire encoding) and any broker, including one that drops or rewrites User Properties.
- The 65,535-byte limit of an MQTT UTF-8 Encoded String and the prohibition of U+0000 are from OASIS MQTT 5.0 section 1.5.4, which the spike did not re-read; the slice 2 test author reads it before writing the statement of `SWR-MQTT-0011`.
- How the `ce-` form treats `ce-datacontenttype` in sdk-go (a User Property with that name): not probed. The proposal is to refuse it where it is read, as D-BIND-1 does for HTTP and Kafka.
- The other SDKs (Rust, C#, Python) as peers; whether the absence of a Java binding is permanent.

## Owner decisions

On 2026-10-24, after the spike:

1. **MQTT is a go as a bet.** (The bet itself, with its riskiest assumption, smallest test, success signal and decision date, lives in the Planner and not in this file.)
2. **MQTT ships as an addition in `ce::v4`.** A new `mqtt` binding header like `kafka.hpp`; no published declaration changes, because `raw_headers`, an ordered list, fits User Properties.
3. **Binary-mode attribute names follow the specification text by default** (names unchanged, no prefix), **with an opt-in for sdk-go's `ce-` prefix on read and on write**, an option in the manner of `ce::http::literal_values` (D-HTTP-1). The carrier is chosen by this request: a defaulted trailing template parameter naming a policy type, with `unprefixed_names` the default and `prefixed_names` the opt-in; ADR-0014 gives the reasons and the alternative declined.
4. **Two slices.** Slice 1: structured mode for MQTT 5.0 and 3.1.1 (3.1.1 has no properties, so only structured mode and a message with no headers). Slice 2: binary mode for 5.0, with the prefix option.

On 2026-10-25, when the owner approved this request and its stage plan:

5. **A foreign User Property in a binary-mode message is ignored** (former open question 1, proposal accepted as written). A User Property whose name is not a valid attribute name (for example `x-request-id`) is skipped and the rest of the message is read, because refusing it would make every broker-side annotation fatal. A name that is a valid attribute name is an extension under the unprefixed rule. Under `prefixed_names` a name without `ce-` is ignored in every case, as sdk-go ignores it. This is `SWR-MQTT-0013`; its statement is unchanged.
6. **A User Property named `content-type` beside the Content Type property is refused with `invalid_argument`** (former open question 2, proposal accepted as written), where the binding reads or writes. The alternative, dropping it silently, is declined. This is `SWR-MQTT-0008`; its statement is unchanged.
7. **The stage plan is approved as written**: slice 1 (structured mode, MQTT 5.0 and 3.1.1), slice 2 (binary mode on 5.0 with the prefix option), then release preparation.
8. **Moving entry points are not ruled.** The question stays open (open question 3 below); the stage plan carries no requirement for a `from_message_moving` in MQTT.

## What this costs

The author's estimate from the spike, not a measurement (`docs/spikes/mqtt.md`, "Cost against the earlier bindings"):

- **Slice 1**: about +700 lines over 16 files, a header of 170 to 220 lines, a test of 300 to 400 lines, a fuzz target of about 80 lines, the CMake target, the install entry and the module export. Size S.
- **Slice 2**: about +500 lines. Size S to M.
- **Interop**: about +1,500 lines, mostly goldens; the generator exists (295 lines, pull request 112), a C++ producer of about 200 lines and a Go verifier of about 100 more are new. The evidence is weaker than Kafka's because there is no Java peer.
- **Documentation**: three decisions in `docs/DECISIONS.md` (the name rule and opt-in, foreign properties, the 3.1.1 entry points), a `docs/GUIDE.md` section and a `docs/SPEC.md` line moving MQTT from "out of scope" to a delivered binding.
- **Ongoing**: two behaviours of one binary mode to keep tested, and a pinned divergence from the only peer.

## Alternatives considered and declined

The table is ADR-0014's; the short form is here.

- **Follow sdk-go everywhere (`ce-` always).** Breaks a MUST of the text.
- **The text only, with no opt-in.** Leaves binary mode with no peer and no external check.
- **An options aggregate in place of a policy type.** The prefix is a compile-time member of the traits; reopenable as an addition if a second option appears.
- **A reserved-name trait in the core.** Declined for now (verdict d).
- **Guessing 3.1.1 in `from_message`.** Wrong on one side; the entry point names the version.
- **Waiting for Protobuf.** Not an alternative to this bet: CR-0006 ranked MQTT first by cost, and the Protobuf spike is a separate request (CR-0009).

## Stages

1. **Slice 1: structured mode, MQTT 5.0 and 3.1.1.** Spec first: `SWR-MQTT-0001` to `SWR-MQTT-0008`, `SWR-MQTT-0014`, `SWR-MQTT-0016` to `SWR-MQTT-0019` and `SYS-MQTT-0001` move to `approved` as their suites are written (`SWR-MQTT-0008`, as ruled in item 6). Then tests first, with `// spec:` markers; then `binding/mqtt.hpp`, `ce::binding_mqtt`, the install entry, the module export, the fuzz target and its corpus, the interop producer and verifier over the structured goldens, `docs/GUIDE.md`, `docs/SPEC.md` and the `D-MQTT-*` decisions. Gates: the matrix of `CLAUDE.md` (gcc-cxx20, gcc-cxx23, clang-cxx20, reflect-cxx26), the three specification gates, the frozen-API diff, the 10-minute fuzz of the new target.
2. **Slice 2: binary mode for 5.0 with the prefix option.** Starts when slice 1 merges. Spec first: `SWR-MQTT-0009` to `SWR-MQTT-0013` and `SWR-MQTT-0015` move to `approved`, and `SWR-MQTT-0011` gains the length limit after OASIS 1.5.4 is read; the binary branch of the target, the binary goldens and the guide section follow.
3. **Release preparation**, following `docs/RELEASE.md`: the `CHANGELOG`, `delivered_in` on the requirements, the ten-minute fuzz on the merge commit and the signed tag, which the owner creates. Whether this is v0.7.0 or a patch release is the owner's call; the request makes no change that forces a minor.

Each stage is a pull request that includes the tests for the code it adds (`CLAUDE.md` workflow rule 7).

## Open questions for the owner

Questions 1 and 2 were ruled on 2026-10-25 and are items 5 and 6 of "Owner decisions". One question remains.

3. **Moving entry points.** CR-0005 gave HTTP, Kafka and NATS a `from_message_moving`, and the spike's sketch left it out. **Proposal:** add `from_message_moving` to the MQTT binding in slice 2, under the same name and the same contract (`SWR-BIND-0014` to `SWR-BIND-0016`), as a further requirement; the owner decides whether it belongs in this bet. **Not ruled.** No requirement is written for it until then, and neither slice waits for the answer.

Smaller choices made in the requirements, which the owner may overrule: a duplicate `datacontenttype` User Property is accepted when equal to the Content Type and refused when different (`SWR-MQTT-0010`); a batch Content Type is refused, not read as a single event (`SWR-MQTT-0006`); the Payload Format Indicator is not written (the text is silent and sdk-go sets nothing).

## Acceptance

- `ce::mqtt::to_message`, `from_message`, `to_payload` and `from_payload` build and pass under `-std=c++20`, `-std=c++23` and the C++26 reflection job with `-Werror`.
- The frozen-API diff finds only additions; `message.hpp` and `binding/common.hpp` are unchanged by both slices.
- Every Go structured golden decodes to the event Go encoded (slice 1); every Go binary golden decodes under `prefixed_names`, and each is `not_a_cloudevent` under the default (slice 2).
- Binary output under the default has no User Property name starting with `ce-` and decodes back; under `prefixed_names` every name starts with `ce-`.
- The MQTT fuzz target replays its seed corpus on every pull request and completes ten minutes in the nightly job.
- The three specification gates and `derive_delivered_in.py --check` stay green at every commit.
