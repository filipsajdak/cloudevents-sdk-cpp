# CR-0009: A Protobuf event format, hand-written, in two slices

> **Status, 2026-10-25.** Approved.
> The owner ruled four things on 2026-10-24 (items 1 to 4 of "Owner decisions") and, on 2026-10-25, accepted all 15 proposals that had kept the request `proposed` (items 5 to 19, one for each former open question, in the same order).
> Each is written below as the accepted rule in full, so no reader has to infer it.
> The request has no open question. Points A to C of the first list were answered the same day (items 20 to 22), and points D and E on 2026-10-27 (items 23 to 26). Slice 2 has six details left for the owner, under "Needs an owner answer before the code (slice 2)"; they are choices of signature, not of principle.
> The requirements are `reviewed` with no `satisfied_by` or `verified_by`, the status of CR-0004 stage 1 and CR-0005: `check_trace.py` requires a `verified_by` only from `approved`, and each moves to `approved` in the stage that writes its suite.
> On 2026-10-27 the statements of `SWR-PROTO-0019` to `-0021` and `-0023` changed (now version 2) to name the entry points.
> Four statements changed with the rulings (`SWR-PROTO-0006`, `-0007`, `-0008` and `-0010`, now version 2) and three requirements were added for rulings that had no home (`SWR-PROTO-0024` to `-0026`).
> The decision is [ADR-0015](../../adr/0015-a-hand-written-protobuf-format.md). No library code, CMake file or CI file changes in this request.

## What prompted this

CR-0006 ranked six candidates and proposed a bet on the Protobuf format, first slice a format-only API, with a spike of at most one week, a pivot signal and a decision date of 2026-11-11.
The spike ran on 2026-10-22 (pull request 113, `docs/spikes/protobuf.md`, with goldens under `interop/protobuf-spike/`; merged).
On 2026-10-24 the owner read it and ruled that the bet goes ahead (items 1 to 4).
This request turns the spike into a specification: requirements, a decision, the cases that do not map and what to ask the owner.

The spike's result in one line: the Go and Java SDKs agree on the schema and on every attribute type, decode each other's bytes, and agree on bytes for 1 of 13 events; no case needs a break; a hand-written reader and writer measured 455 formatted lines and round-trips both SDKs.

## Owner decisions

On 2026-10-24:

1. **Protobuf is a go as a bet, and ships as an addition in `ce::v4`**: a new format header and target, and no change to a published declaration. Recorded with the pivot signal below.
2. **The codec is hand-written.** No `libprotobuf`, no generated code, and the core stays CTRE-only. The spike's prototype measured 455 lines formatted and round-trips both SDKs. The wording change to the dependency constraint that CR-0006 proposed for a format with a third-party library is therefore **not needed**, and no file named in that table is edited. Because the codec parses untrusted bytes, a fuzz target is required from the first slice (`SWR-PROTO-0017`); the limits on nesting, length and overflow are named constants, confirmed by the owner on 2026-10-25 (item 5).
3. **Writing follows the specification, reading accepts everything.** The encoder writes `text_data` for string payloads; the decoder accepts `binary_data`, `text_data` and `proto_data` from either SDK. The Go SDK's difference is a known limitation and an interoperability finding (next section), recorded as D-INTEROP-5 recorded the Kafka findings.
4. **The field numbers follow `cloudevents.proto` at `v1.0.2`, not the prose of `protobuf-format.md`.** Evidence is in "The pivot signal and the evidence for the decisions".

On 2026-10-25 the owner accepted all 15 proposals of the former "Open questions" as written. Each is recorded here as the accepted rule; items 5 to 19 correspond to former questions 1 to 15, in order.

5. **Decode limits** (`SWR-PROTO-0010`). The nesting depth is fixed by the schema (event, map entry, value, `Timestamp`; `Any` is opaque; groups are refused), so it is a constant and not an option. Named constants in `ce::protobuf`: `default_max_encoded_size` = 16 MiB, `default_max_attribute_count` = 1024, `max_varint_bytes` = 10 (the wire format's own bound), `fixed_nesting_depth` = 4. The encoded size and the attribute count are fields of `protobuf::decode_options` that default to those constants; both checks happen before an allocation. The values were not measured against a workload.
6. **Timestamps.** Decode gives UTC, with the fewest digits that hold the nanoseconds (0, 3, 6 or 9). A Timestamp outside the range of `ce::timestamp` (about the years 1678 to 2262), or with nanos outside 0 to 999999999, is `invalid_timestamp`, as the JSON decoder refuses the same instant. Widening the type is a break and is not done. The guide states the loss of the offset and of the fraction digits.
7. **Empty `binary_data` against no data.** Write no field for an event without a payload, and a `binary_data` of length 0 for an empty `binary`. Read an empty `binary_data` in an event with no `datacontenttype` as no payload, and an empty `binary_data` in an event with a `datacontenttype` as an empty `binary`. The consequence, accepted with the ruling: an empty `binary` payload of an event with no `datacontenttype` is read back as no payload. The alternative, always an empty `binary`, was declined.
8. **JSON-typed data.** The default decode keeps returning `std::string` for `text_data` and `binary` for `binary_data`, as the wire says. An optional `protobuf_format::decode_as<Codec>` (a new name) classifies the payload by `is_json_content_type`, as the bindings do. The retention wording of the first acceptance is superseded by item 21: there is no retention. Stage 1 also checks that a `json_document` can be written as text without a codec argument. This is `SWR-PROTO-0025`.
9. **A `proto_data` type URL that differs from `dataschema`.** On write, `proto_data` is used only for a `binary` payload whose `datacontenttype` is `application/protobuf` and that has a `dataschema`; `dataschema` is written as the type URL; every other payload goes to `binary_data` or `text_data`. On read, the `Any` value is given as a `binary` payload, `datacontenttype` is set to `application/protobuf` if absent, and `dataschema` is set to the type URL if absent. When both are present and differ, `dataschema` is kept and the URL is lost. A side channel, without a break: `protobuf_format::decode_detailed`, returning the event and the `Any` type URL, and `encode_proto_data(event, type_url)`. This is `SWR-PROTO-0026`.
10. **Batch in slice 1.** Yes, as format functions only: `encode_batch(std::span<const event>)` and `decode_batch(...)` returning `std::vector<event>`, with the `protoc` golden as its evidence, a media type constant for `application/cloudevents-batch+protobuf`, and no binding batch mode. The accepted requirement: the `protobuf_format` class shall provide `encode_batch` and `decode_batch` for a `CloudEventBatch` message, expose `application/cloudevents-batch+protobuf` as its media type, and apply the limits of `SWR-PROTO-0010` to the count of events (made specific by item 20). This is `SWR-PROTO-0024`.
11. **Binding entry-point names** (slice 2). New names per binding, for example `http::to_message_protobuf` and `http::from_message_protobuf`, and the same in Kafka and NATS, with no change to the published `from_message`. A NATS payload has no content type, so its Protobuf entry points take the format explicitly. Structured mode stays hard-wired to JSON in the published entry points.
12. **`from_message` does not detect `application/cloudevents+protobuf`.** Detection would change the result of a published entry point for a message it refuses today (`SWR-PROTO-0022`).
13. **Type URL policy for `proto_data`.** Write the URL verbatim from `dataschema`, with no `type.googleapis.com/` prefix added, as sdk-go does. Accept any URL on read: the `Any` is opaque and the format has no registry.
14. **Extension attribute value types.** Return the type of the wire arm, so a Protobuf round trip keeps `binary`, `uri`, `uri_ref` and `timestamp`, which JSON cannot. A `ce_uri_ref` extension is read as `uri_ref`, which sdk-java does not do.
15. **String and byte limits.** No separate limit: no field may exceed the remaining input, and the encoded-size limit of item 5 bounds the rest.
16. **The decision date 2026-11-11** of the CR-0006 bet stays, as the review of slice 1: persevere, pivot or stop, with the signals of the bet and the measured fuzz result.
17. **Upstream reports.** The sdk-go and specification findings (`text_data` never written, the quoting of JSON read from `text_data`, the prose against the `.proto`) are to be reported upstream. This request tracks none of them.
18. **Where the goldens live.** Stage 1 moves the spike's goldens from `interop/protobuf-spike/` to `interop/protobuf/`, laid out as `interop/kafka` is, and leaves the spike's generators in place until then.
19. **No `std::string_view` overload of `decode`.** A `std::span<const std::byte>` only; `message::body` is already that.

On 2026-10-25, later, the owner answered points A to C of "Needs an owner answer before the code":

20. **Batch limits (point A).** The encoded-size limit and the attribute-count limit of item 5 apply to each event of a batch. The batch has its own named constant for the number of events, `default_max_batch_event_count`, in `ce::protobuf`, proposed at 100,000 events and adjustable: the owner may change the value in the review of the implementing pull request. Decoding a batch with more events fails with `out_of_range` before an allocation for them. This updates `SWR-PROTO-0010` and `SWR-PROTO-0024`.
21. **`decode_as` holds no document (point B).** There is no retention. `decode_as<Codec>` is a plain typed read: a JSON-typed payload stays text or bytes in the event, and `decode_as` parses it into the codec's value on demand without holding a document. `protobuf::decode_options` carries only the decode limits. This updates `SWR-PROTO-0025`.
22. **The `proto_data` type URL (point C).** An empty type URL counts as absent: no `dataschema` is set from it. A non-empty type URL that is not a valid URI-reference fails with `parse_error`. On encode, the codec writes the `Any` type URL given through the side channel and also writes `dataschema` as its own attribute, even when they differ, so nothing is lost silently. This updates `SWR-PROTO-0007`, `-0008` and `-0026`.

On 2026-10-27 the owner answered points D and E:

23. **Entry-point names (point D, part 1).** `to_message_protobuf` and `from_message_protobuf` in each of `http::`, `kafka::` and `nats::`. NATS also gets `to_payload_protobuf` and `from_payload_protobuf` for its payload form: the published NATS names are `to_payload` and `from_payload`, so the Protobuf ones are the same stems plus `_protobuf`. The published JSON entry points are unchanged (`SWR-PROTO-0022`). Declined: a policy template parameter on the published templates, which risks changing published declarations. This makes item 11 exact. `SWR-PROTO-0019` to `-0021`.
24. **The NATS format carrier (point D, part 2).** The name of the entry point carries the format: `nats::from_payload_protobuf(bytes)` always means Protobuf, with no tag argument. Declined: a tag overload on a published function. `SWR-PROTO-0021`.
25. **A wrong content type (point D, part 3).** `from_message_protobuf` returns `errc::not_a_cloudevent` for a message whose content type is not `application/cloudevents+protobuf`. HTTP and Kafka check the content type. A NATS payload has none, so `from_payload_protobuf` decodes any bytes and `parse_error` covers garbage. Declined: decode anyway. `SWR-PROTO-0019` and `-0020`, `-0021`.
26. **Upstream reports (point E).** The owner files them; an agent drafts the issue texts, which are not kept in this repository. This request tracks none, as item 17 said, and the process point is closed.

## The pivot signal and the evidence for the decisions

**The pivot signal was met read literally, and the owner went ahead.**
The CR-0006 bet said: pivot to MQTT or stop if "the two SDKs disagree on a v1.0.2 MUST".
The spike found one: the specification says text data MUST be stored in `text_data`, and sdk-go has no code path that writes `text_data`; it writes `binary_data` for everything but `application/protobuf`.
The spike read this as wire-compatible and one SDK deviating, the shape D-NATS-1 already accepted, and left the signal to the owner.
**The owner ruled on 2026-10-24 to go ahead.** That is the record of the decision against the signal; the decision date of 2026-11-11 stays (item 16).

| finding | evidence (from the spike) | consequence here |
|---|---|---|
| the prose and the `.proto` number differently | `.proto`: `attributes` 5, `binary_data` 6, `text_data` 7, `proto_data` 8. Prose: attributes 1, data 2 to 4. Both SDKs implement the `.proto`; the goldens decode against it with `protoc` | the `.proto` wins (decision 4, `SWR-PROTO-0003`); under rule 5 of `CLAUDE.md` the discrepancy is reported, and the owner agreed on 2026-10-25 to report it upstream (item 17) |
| sdk-go never writes `text_data` | 13 goldens: `binary_data` for `text_data`, `text_data_empty`, `data_array` and `full` | the encoder follows the specification; the decoder accepts both |
| sdk-go quotes a JSON `text_data` | sdk-go reads a `text_data` of `application/json` and returns it as a JSON string (`"{\"count\":3,...}"`) | a known limitation of sdk-go as a reader; the interop test records it and does not hide it |
| the SDKs agree on bytes for 1 of 13 events | map order (random in sdk-go), empty `binary_data` for no data in sdk-go, `ce_uri` against `ce_uri_ref` for a relative `dataschema`, the `Any` type URL | no byte comparison; decode-equal comparison, and a deterministic encoder |
| neither SDK validates on decode | `spec_version` 0.3, an empty `id`, `time` sent as a string, a negative `nanos` all accepted | the decoder validates, as the JSON decoder does (`SWR-PROTO-0009`) |

## What is requested

**Slice 1: the format, bytes to event and event to bytes**, for a single event.

- `protobuf_format::encode(const event&) -> result<binary>` and `protobuf_format::decode(std::span<const std::byte>, protobuf::decode_options = {}) -> result<event>` (working names), header-only, standard library and `ce::core` only (`SWR-PROTO-0001`, `-0013`, `-0014`).
- The wire schema is `cloudevents.proto` at `v1.0.2`: required attributes as fields 1 to 4, every other attribute as a map entry, three data fields (`SWR-PROTO-0003`, `-0004`).
- Attribute types are kept: Protobuf carries them (`SWR-PROTO-0005`). A decoded `time` is UTC; the offset and the digits of the fraction are lost (`SWR-PROTO-0006`).
- The writer follows the specification, the reader accepts every form (`SWR-PROTO-0007`, `-0008`).
- Decode is strict and uses existing error codes (`SWR-PROTO-0009`), within named limits (`SWR-PROTO-0010`); encode is deterministic (`SWR-PROTO-0011`); an accepted input re-encodes (`SWR-PROTO-0012`).
- Batch as format functions only, `encode_batch` and `decode_batch` (`SWR-PROTO-0024`); an optional `decode_as<Codec>` that classifies JSON-typed data (`SWR-PROTO-0025`); the `proto_data` side channel `decode_detailed` and `encode_proto_data` (`SWR-PROTO-0026`).
- Evidence: offline goldens from sdk-go, sdk-java and `protoc` (`SWR-PROTO-0016`), a fuzz target (`SWR-PROTO-0017`), the guide (`SWR-PROTO-0018`), the module export in `ce::v4` only (`SWR-PROTO-0015`).

**Slice 2: structured mode in the bindings**, with the media type `application/cloudevents+protobuf`, as new entry points in the HTTP, Kafka and NATS bindings (`to_message_protobuf` and `from_message_protobuf` in each, `to_payload_protobuf` and `from_payload_protobuf` also in NATS; items 23 to 25), and interoperability through them (`SWR-PROTO-0019` to `-0023`).
The batch format is in slice 1, as format functions only (item 10, `SWR-PROTO-0024`); the bindings have no batch mode.

### Error codes

Every decode failure maps to an enumerator that exists; none is added.

| failure | `errc` |
|---|---|
| truncation, a length beyond the buffer, a varint over ten bytes, an unskippable wire type (a group) | `parse_error` |
| an id, source or type absent or empty | `missing_required_attribute` |
| a `spec_version` other than `1.0` | `unsupported_spec_version` |
| a string that is not UTF-8 | `invalid_utf8` |
| a `ce_integer` outside the range of `int32`; input or map above a limit | `out_of_range` |
| an attribute value with no arm | `invalid_attribute_value` |
| `time`, `datacontenttype`, `dataschema` or `subject` in the wrong arm | `type_mismatch` |
| a Timestamp with nanos outside 0 to 999999999, or an instant the timestamp type cannot hold | `invalid_timestamp` |

## Interoperability evidence

The offline-evidence pattern of `SWR-SEC-0008` and D-INTEROP-5: bytes recorded from the SDKs, committed with their generators and verifiers, no broker and no network in a test.
The spike committed 13 events from sdk-go v2.15.2 (protobuf-go v1.26.0) and from sdk-java 2.5.0 (protobuf-java 3.15.0), and 13 cases built by `protoc` 36.2 from the `v1.0.2` `.proto`, and one two-event batch.
Stage 1 moves what it needs from `interop/protobuf-spike/` to `interop/protobuf/` (item 18), adds a C++ producer, and adds the Go and Java readers of the bytes the C++ side writes.
The comparison is decode-equal, never byte-equal, for the reasons in the table above; sdk-go output needs `Deterministic: true`.
A difference between the SDKs is recorded as a decision in `docs/DECISIONS.md`, and the goldens are not edited to hide it.
Known differences already found, to be recorded as D-INTEROP-6 or the next number by the stage: `text_data` never written by sdk-go; sdk-go quotes JSON read from `text_data`; sdk-go drops a `ce_uri_ref` `dataschema`; sdk-java reads a `ce_uri_ref` extension as a URI; sdk-go percent-encodes a non-ASCII `source`.

## What this costs

- **Maintained code.** About 455 to 480 formatted lines for one event and batch, plus a test file, a fuzz target and an interop harness; CR-0006 estimated M to L and the spike measured M.
- **A hand-written parser of untrusted bytes.** It has no years of hardening behind it. The answer is the fuzz target, named limits and strict decoding, all in slice 1. The prototype's smoke run (1,000,000 mutated inputs under ASan and UBSan, no report) is not a campaign.
- **Information lost in the mapping**, listed above and stated in the guide (`SWR-PROTO-0018`).
- **Two upstream defects in sdk-go**, which this request does not fix and does not track.
- **A format that no one has asked for.** CR-0006 decision 1: no consumer waits; the bet is the owner's.

## Alternatives considered and declined

- **`libprotobuf`.** Declined by the owner on 2026-10-24: the first compiled dependency, version-matched codegen, two packaging ports, a rewording of the dependency constraint. See ADR-0015.
- **The prose numbers.** Not on the wire in either SDK.
- **A `proto_any` alternative in `data_t`.** A break; declined here and not proposed.
- **MQTT first.** The pivot named in CR-0006. The owner went ahead with Protobuf.
- **Binding integration before the format.** CR-0006 recommended format-only first; the format needs no transport.

## Needs an owner answer before the code (slice 2)

The rulings fix the names, the format carrier and the content type rule. These details are not ruled; each has a proposal, and the stage waits for the answers.

| # | detail | proposal |
|---|---|---|
| F | The signatures. `to_message_protobuf` and `from_message_protobuf` take what, and what do they accept? | `to_message_protobuf(const event&) -> result<message>` with no `content_mode` argument, as the only mode is structured and a batch is a format function (item 10). `from_message_protobuf(const message&, protobuf::decode_options = {}) -> result<event>`. `to_payload_protobuf(const event&) -> result<binary>` and `from_payload_protobuf(std::span<const std::byte>, protobuf::decode_options = {}) -> result<event>`, as item 19 gave `decode`. None is a template, as no codec takes part. |
| G | A batch event. What does `to_message_protobuf` do with a batch? | Nothing special: it takes one `event`, and the bindings have no batch mode (item 10). A batch stays `protobuf_format::encode_batch`. |
| H | The content type check. Is the media type compared ignoring case and ignoring parameters (`; charset=...`)? | Yes, as `detect_content_mode` compares the JSON types. Header lookup keeps the casing rule of each binding's existing lookup (`Content-Type` in HTTP and NATS, `content-type` in Kafka as it is there), and `to_message_protobuf` writes the header name the binding writes for JSON structured mode. |
| I | The NATS message form. `nats::from_message_protobuf` reads a message that has headers. Does it check the content type (as HTTP) or decode any body (as the payload form)? Ruling 25 says NATS has none, which is true of the payload form only. | It checks, like HTTP and Kafka, because the message form has a `Content-Type` header and `to_message_protobuf` writes one; the payload form decodes any bytes. |
| J | The Kafka key. Does `kafka::to_message_protobuf` set a key? | No, as in JSON structured mode: the key is the caller's. |
| K | Moving variants. Does stage 2 add a `from_message_protobuf_moving`? | No. The decoder copies out of the body, so a move has nothing to gain (and CR-0005's moving entry points exist for a body adopted into the event). Revisit with a measurement. |

## Acceptance

- Slice 1: a `protobuf_format::decode` of every golden recorded from sdk-go and sdk-java returns the event they encoded, modulo the documented losses; both SDKs decode what `encode` writes to the event this SDK encoded; the decoder refuses every `protoc` edge case with the error code in the table; the fuzz target replays its corpus on every pull request and completes ten minutes in the scheduled job.
- No published declaration changes: the frozen-API diff (`python3 scripts/frozen_api_diff.py --base <last tag>`) passes, and `ce::v3`, `ce::v2` and `ce::v1` have no declaration of the format.
- The core's dependency list is unchanged: CTRE only.
- Slice 2: each binding writes and reads structured mode in Protobuf, the JSON entry points return what they return today for every input, and the interop tests pass through the bindings.
- The three specification gates and `derive_delivered_in.py --check` stay green at every commit.
