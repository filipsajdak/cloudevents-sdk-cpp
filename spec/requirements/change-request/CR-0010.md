# CR-0010: Binary mode refuses a datacontenttype that a reader takes for a CloudEvents format

> **Status, 2026-11-09.** Approved: the owner ruled the fix on 2026-11-09 (see "Owner ruling").
> The owner ruled the remaining questions the same day: the refusal is a defect fix released as v0.7.1 (see "Versioning"), the frozen generations are left as they are and their exposure is documented (see "Frozen generations"), and the readers do not trim (see "Leading whitespace"). No question is open.

## What prompted this

The scheduled fuzz run of 2026-11-07 crashed `fuzz_mqtt_message` on the commit tagged v0.7.0, `801c4a2`
(<https://github.com/filipsajdak/cloudevents-sdk-cpp/actions/runs/42363661076>).
The crash input minimises to a structured MQTT 5.0 message, Content Type `application/cloudevents+json`, whose payload is this event:

```json
{"specversion":"1.0","id":"1","source":"/","type":"t","datacontenttype":"application/cloudevents"}
```

The message decodes. Written back in binary mode it succeeds, with the Content Type property `application/cloudevents`, because binary mode carries `datacontenttype` there (`SWR-MQTT-0009`).
Read back, the reader sees a Content Type that starts with `application/cloudevents` and takes the message for structured mode (`SWR-MQTT-0004`), so it parses the empty payload as a JSON event and fails with `parse_error`.
The harness checks that what binary mode wrote reads back, and aborted.
The run is not a memory error: AddressSanitizer and UndefinedBehaviorSanitizer report nothing, and the abort is the harness's own check.

## The defect

Binary mode writes `datacontenttype` into the content-type field, and every reader decides the mode from that same field before it looks at anything else.
So an event whose `datacontenttype` starts with `application/cloudevents` writes a binary-mode message that reads back as a structured or batched one.
The data then stands where the reader expects an event:

- data that is not a CloudEvent, or no data, fails to read back (`parse_error`, or `invalid_argument` for the batch media type), so the event is lost at the receiver;
- data that is itself a CloudEvent JSON document reads back as that inner event, so a relay that receives an event in structured mode and forwards it in binary mode hands its consumer a different event from the one it received.

### Evidence, before the fix

Measured with every binding's `to_message(event, binary_mode)` then its `from_message`, nlohmann codec, at `main` after v0.7.0 (`a644a0e`):

| `datacontenttype` of the event | HTTP | Kafka | MQTT, both name policies | NATS |
|---|---|---|---|---|
| `application/cloudevents`, no data (the crash) | write ok, read `parse_error` | write ok, read `parse_error` | write ok, read `parse_error` | reads back |
| `application/cloudevents+json`, data an event with id `inner` | write ok, read **the inner event** | write ok, read **the inner event** | write ok, read **the inner event** | reads back |
| `application/cloudevents-batch+json` | write ok, read `invalid_argument` | write ok, read `invalid_argument` | write ok, read `invalid_argument` | reads back |
| `Application/CloudEvents+json` | write ok, read fails | reads back | reads back | reads back |
| `application/json` (control) | reads back | reads back | reads back | reads back |

The mixed-case row is the readers' own difference: the HTTP reader compares the media type ignoring case (`SWR-HTTP-0006`), the Kafka and MQTT readers byte for byte (`SWR-KAFKA-0004`, `SWR-MQTT-0007`).
NATS is not affected, because its binary mode carries `datacontenttype` as `ce-datacontenttype` and never in the content type (`D-NATS-1`).
MQTT structured mode and MQTT 3.1.1 are not affected: neither writes `datacontenttype` into a content-type field.

Exposure by release: HTTP binary mode since v0.1.0, Kafka since v0.2.0, MQTT since v0.7.0.

## Owner ruling

Ruled by the owner on 2026-11-09:

1. **Binary-mode `to_message` of the HTTP, Kafka and MQTT bindings refuses the event** with `errc::invalid_argument` and produces no message, when its `datacontenttype` starts with `application/cloudevents`.
   The batch media type `application/cloudevents-batch` starts with that prefix and is refused with it.
2. **The writer asks the reader's question.** Each binding's refusal tests the media type as its `detect_content_mode` does, so the two cannot disagree: HTTP ignores case, Kafka and MQTT compare byte for byte, and parameters change nothing because the test is a prefix.
   MQTT shares one function between reader and writer. For HTTP and Kafka a shared function cost about 200 instructions on every binary-mode receive in the perf job, so their readers keep their v0.7.0 text and a test holds the writer's function to the reader's decision for every case (D-BIND-5).
   The test is made after the leading whitespace the media-type grammar admits (see "Leading whitespace").
3. **Structured mode is unchanged**, in every binding. Such an event still travels in structured mode, where `datacontenttype` is a member of the document.
4. **NATS is unchanged**, and a test pins that the same events still read back from NATS binary mode.
5. **One pull request** carries the fix for the three bindings, the fuzz harness checks and the seeds.

## Leading whitespace

A review of the first fix found a bypass on 2026-11-09, and it is real.
The media-type grammar `datacontenttype` is checked against (`content_type_pattern`, `^\s*type/subtype\s*(;.*)?$`) admits whitespace before the type, so `" application/cloudevents+json"` and `"\tapplication/cloudevents+json"` are valid values.
The readers of this SDK do not trim a content type, so within the SDK such an event writes and reads back as itself.
An HTTP field parser drops the leading spaces and tabs of a field value (RFC 9110, 5.5), so a receiver behind one sees `application/cloudevents+json` and reads the message as structured: with the relay input the measured result was the inner event, in all three bindings, once the content type was trimmed as such a parser trims it.
A Kafka or MQTT peer that trims the value would do the same.

The fix tests the value after the whitespace the grammar admits (space, tab, CR, LF, VT, FF), with the same `content_mode_of` the reader uses, so case and prefix are compared exactly as the reader compares them.
The readers are not changed to trim: that would change what `detect_content_mode` returns for a received message (`SWR-HTTP-0006`, `SWR-KAFKA-0005`, `SWR-MQTT-0004`), which is outside this ruling.
The writer therefore refuses a little more than this SDK's own readers would misread. The owner ruled on 2026-11-09 that the readers do not trim.
Trailing whitespace does not move the prefix and needs no rule; a test pins it.

A separate observation, not changed here: the content type is written into the header as it is, without the value policy, so a `datacontenttype` with a leading CR or LF before another media type (`"\r\ntext/plain"`) reaches the `Content-Type` header with a line break in it. An HTTP adapter that writes header values without checking them would emit a broken header. This predates the change; the owner gave it a change request of its own, CR-0012 (reserved).

## Alternatives declined

| alternative | why it was declined |
|---|---|
| Accept the event and document the loss | A caller cannot see the problem until a consumer drops the message or reads another event. The relay case substitutes an event silently, and a documented substitution is still one. |
| Refuse on read: take a message with the `ce-specversion` attribute and a CloudEvents content type for binary mode | It changes what every reader does with every structured message that also carries attribute headers, against the binding texts (section 3 of the HTTP, Kafka and MQTT bindings), which decide by the content type alone. A reader cannot tell a forged structured message from a real one, so the fix belongs where the ambiguity is made. |
| MQTT only, where the fuzz run found it | The same write and the same read exist in HTTP and Kafka; fixing one binding leaves two known instances. |

## Requirements

A new cross-binding requirement states the refusal, in the way `SWR-BIND-0009` and `SWR-BIND-0017` state one rule for several bindings, with each binding's test as its evidence:

- **`SWR-BIND-0019` (new).** When the HTTP, Kafka or MQTT binding of `ce::v4` writes an event in binary mode and the event's `datacontenttype`, after the leading whitespace its media-type grammar admits, starts with `application/cloudevents`, compared the way that binding's `detect_content_mode` compares a received content type, `to_message` shall return `errc::invalid_argument` and produce no message.

Four statements say without exception that binary mode writes `datacontenttype` into the content-type field, or that a decoded event always re-encodes, and each gains the exception (`D-EXT-6`: a statement change bumps the version and returns an `implemented` requirement to `approved` without `delivered_in`):

| requirement | version | the amendment |
|---|---|---|
| `SWR-HTTP-0008` | 1 to 2 | the `Content-Type` mapping holds for an event `SWR-BIND-0019` does not refuse |
| `SWR-HTTP-0015` | 2 to 3 | an event that `to_message` refuses only by `SWR-BIND-0019` is not an error of `from_message`: it decodes from a structured message and re-encodes in structured mode |
| `SWR-KAFKA-0002` | 1 to 2 | the `content-type` mapping holds for an event `SWR-BIND-0019` does not refuse |
| `SWR-MQTT-0009` | 1 to 2 | the Content Type mapping holds for an event `SWR-BIND-0019` does not refuse |

`SWR-HTTP-0003` (to_message returns a message in the mode asked for) and `SWR-BIND-0002` (the core writes the content type last) are not amended: the first already admits a refusal (a batch, a value that is not UTF-8), and the second is about the shared core, which this change does not touch.
`SWR-SEC-0001` (the fuzz targets) is not amended; it is listed because its targets gain the read-back check below.

## Tests planned

Each binding's suite cites `SWR-BIND-0019`; every check runs for each enabled codec.

| suite | file | what it shows |
|---|---|---|
| `binary-mode-refuses-a-cloudevents-media-type` | `test/http_binding_test.cpp` | the minimised input, the relay input, the batch media type, a media type with parameters, one in mixed case and one after leading whitespace are `invalid_argument` with no message; structured mode still writes each; `application/json` still writes and reads back |
| `kafka-binary-mode-refuses-a-cloudevents-media-type` | `test/kafka_binding_test.cpp` | the same inputs, and `to_record` refuses them too; the mixed-case one writes and reads back, because the Kafka reader compares byte for byte |
| `mqtt-binary-mode-refuses-a-cloudevents-media-type` | `test/mqtt_binding_test.cpp` | the same inputs under `unprefixed_names` and `prefixed_names`; the mixed-case one writes and reads back |
| `nats-binary-mode-keeps-a-cloudevents-media-type` | `test/nats_binding_test.cpp` | the pin: NATS binary mode still writes the same events and reads each back unchanged |

The fuzz targets `fuzz_http_message`, `fuzz_kafka_message` and `fuzz_mqtt_message` check that a decoded event either writes in binary mode and reads back as the same `id`, `source`, `type` and `datacontenttype`, or is refused with `invalid_argument` exactly when the binding's own predicate says the media type is a CloudEvents format.
A full equality is not checked: an extension's type and a JSON payload's representation legitimately change on a binary round trip (`docs/GUIDE.md`, "Comparing an extension after a round trip"; `D-JSON-4`).
The minimised crash input becomes a seed of `fuzz_mqtt_message`, and the same event in an HTTP and a Kafka message becomes a seed of the other two.

## Versioning

`D-BUILD-4` counts "a change to behaviour the published documentation states" as a break, and a break goes to a new generation with a minor version.
The evidence for both readings is kept below.

**Owner decision, 2026-11-09: a defect fix, not a break.** The refused message never read back as the event sent, so no caller could rely on it. The release is v0.7.1, a patch (D-BUILD-5); no `ce::v5` and no exception is needed.

Evidence that it is a **break**:

- `SWR-HTTP-0008` (v0.1.0), `SWR-KAFKA-0002` (v0.2.0) and `SWR-MQTT-0009` (v0.7.0) state without exception that binary mode writes `datacontenttype` into the content-type field, and this request amends all three.
- `SWR-HTTP-0015` (v0.4.0) states that an event `from_message` returns re-encodes, and the fuzz target of HTTP checked it for binary mode, so an event that decodes and is now refused in binary mode is a stated behaviour that changes.
- The guide's binding table says that `datacontenttype` "travels as" `Content-Type` and `content-type`, and the v0.7.0 changelog says MQTT binary mode writes a PUBLISH "whose Content Type property is `datacontenttype`", without exception.
- A caller that wrote such an event in binary mode got a message back before and gets `invalid_argument` now.

Evidence that it is a **fix**:

- No document says that binary mode accepts any `datacontenttype`, or names this event as one that round-trips; `docs/GUIDE.md` and `README.md` show binary mode only with `application/json` and `text/plain`.
- The result removed could not do what binary mode is for: it read back as `parse_error`, `invalid_argument` or another event, never as the event written. The binding texts decide the mode by the content type first (section 3 of the HTTP, Kafka and MQTT bindings), so no reader that follows them takes the message for the binary-mode message of that event.
- The v0.4.0 changelog lists a new refusal on the way out (ill-formed UTF-8 under the percent-encoding policy) under "Fixed".
- No declaration changes: `scripts/frozen_api_diff.py --base v0.7.0` passes.

## Frozen generations

The binary-mode writers of `ce::v1`, `ce::v2` and `ce::v3` are copies, and each has the defect for HTTP and Kafka (MQTT exists in `ce::v4` only):

| generation | published by | HTTP binary mode | Kafka binary mode |
|---|---|---|---|
| `ce::v1` | v0.3.0 | exposed | exposed |
| `ce::v2` | v0.4.0 | exposed | exposed |
| `ce::v3` | v0.5.0 | exposed | exposed |
| `ce::v4` | v0.6.0 | fixed by this request | fixed by this request |

Rule 4 lets a frozen generation take a fix that keeps its declarations (`D-CODEC-3`), so the change could be made there as a body-only change.
**Owner decision, 2026-11-09: the frozen copies are left as they are.** No `ce::v1` to `ce::v3` code changes. The exposure is documented instead: a "Known limitations" entry in the changelog and a sentence in the guide tell a caller to use `ce::v4` or to filter out a `datacontenttype` that starts with `application/cloudevents` before writing in binary mode.
`SWR-BIND-0019` names `ce::v4`, so no requirement claims the frozen copies.

## Found while fixing (kept out by the owner)

An event with binary data (`data_base64`) under a JSON media type, for example `{"datacontenttype":"application/json","data_base64":"AAAA"}`, decodes from structured mode and writes in binary mode in HTTP, Kafka, MQTT and NATS, and the reader then parses the bytes as JSON and fails with `parse_error`.
The event is lost but never replaced. `fuzz_mqtt_message` at v0.7.0 already traps on it, so the scheduled run can find it next.
The owner ruled on 2026-11-09 to keep it out of this request: the fuzz targets carve it out of the read-back check (they still require its binary write to succeed), the changelog lists it as a known limitation, and a follow-up change request, CR-0011 (reserved), decides between refusing it on write and accepting it on read (D-BIND-5).

## Rule 4 and the API

The change adds declarations and changes function bodies of `ce::v4` only:

- `binding::detail::cloudevents_media_type_prefix` and `batch_media_type_prefix`, the named prefixes the HTTP and Kafka readers and writers share (the MQTT binding keeps its own, published at v0.7.0 and unchanged);
- `http::detail::content_mode_of`, `kafka::detail::content_mode_of` and `mqtt::detail::content_mode_of`, each the media-type test its binary-mode `to_message` calls, which MQTT's `detect_content_mode` calls too and which a test holds to the HTTP and Kafka `detect_content_mode`;
- `binding::detail::media_type_whitespace` and `without_leading_whitespace`, the whitespace a transport may drop before the prefix test;
- a `binding::detail` helper that returns the refusal.

No declaration is removed or changed, and `detect_content_mode` returns what it returned for every message.

## Acceptance

The implementing pull request carries the requirement, the amendments, the suites above, the fuzz checks and seeds, a changelog entry under "Fixed", a note in the guide's HTTP, Kafka and MQTT sections and a `D-BIND` entry, and passes the frozen-API gate against v0.7.0.
