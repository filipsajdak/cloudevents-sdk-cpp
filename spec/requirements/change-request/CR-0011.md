# CR-0011: Binary mode refuses binary data that its JSON media type makes unreadable

> **Status, 2026-11-09.** The owner ruled the direction on 2026-11-09 (see "Owner ruling"): refuse on write.
> The analysis below presents the evidence and does not rule: whether the change is a fix or a break, where the refusal names its cause, the behaviour with `parse_binary_body = false`, and NATS are left to the owner (see "Open questions for the owner").
> This request builds on CR-0010 and its `SWR-BIND-0019`, which are on `main` (pull request #133, merged): the amendments below start from the versions on `main`.

## What prompted this

The scheduled fuzz run of 2026-11-07 that found the defect of CR-0010 (<https://github.com/filipsajdak/cloudevents-sdk-cpp/actions/runs/42363661076>, the commit tagged v0.7.0) also showed a second one, which `CR-0010` ("Found while fixing") kept out of its scope.
`fuzz_mqtt_message` at v0.7.0 traps on it, and the fuzz targets on `main` carve it out of their read-back check (`ce_fuzz::binary_under_json`) until this request decides it.

The probe is this event, whose `data_base64` bytes are `00 00 00`:

```json
{"specversion":"1.0","id":"1","source":"/","type":"t","datacontenttype":"application/json","data_base64":"AAAA"}
```

It decodes, as every binding's structured decode takes `data_base64` to a `ce::binary` payload whatever the media type.
Written in binary mode it succeeds in HTTP, Kafka and MQTT: the body is the three bytes and the content-type field is `application/json`.
Read back, the reader sees a JSON media type, parses the body (`SWR-BIND-0008`), and fails with `parse_error`.

## The defect

`write_body` writes a `ce::binary` payload as the body, without looking at the media type, and the v4 reader parses every non-empty binary-mode body under a media type that `is_json_content_type` accepts.
So an event with binary data under a JSON `datacontenttype` writes a message that its own reader refuses unless the bytes happen to be JSON.
The event is lost at the receiver and never replaced: the result is `parse_error`, not another event, which is the difference from the relay case of CR-0010.

### Evidence, before the change

Measured with each binding's `to_message<nlohmann_codec>(event, binary_mode)` then its `from_message<nlohmann_codec>`, on the commit this branch is built on (the tree of `main` after #133), g++ 16, by decoding the JSON document above with `data_base64` and `datacontenttype` as given:

| `datacontenttype` | `data_base64` | HTTP | Kafka | MQTT 5.0 | NATS |
|---|---|---|---|---|---|
| `application/json` | `AAAA` (bytes that are not JSON) | write ok, read `parse_error` | write ok, read `parse_error` | write ok, read `parse_error` | write ok, read `parse_error` |
| `application/json` | `eyJhIjoxfQ==` (the bytes `{"a":1}`) | reads back | reads back | reads back | reads back |
| `text/plain` (control) | `AAAA` | reads back | reads back | reads back | reads back |

The second row reads back as a JSON payload (a `json_document` or `json_text`), not as the `ce::binary` that was written: the bytes are kept, the payload alternative changes (`D-JSON-4` already accepts a changed JSON representation on a binary round trip).

**NATS has the same defect.** The assumption that its reader would keep the body as binary does not hold: the NATS reader takes `datacontenttype` from the `ce-datacontenttype` header (`D-NATS-1`) and then calls the same `binding::read_body`, which parses under a JSON media type.
CR-0010's defect is absent from NATS because the mode is decided by a `Content-Type` header that NATS does not write for `datacontenttype`; this defect does not depend on where the media type travels, only on the reader's parse.
`fuzz_nats_payload` does not check a binary-mode read-back, which is why no run found it.
The probe measured it for all four bindings; the owner's ruling names three (see "Open questions for the owner", question 1).

Exposure by release: HTTP binary mode since v0.1.0, Kafka since v0.2.0, MQTT since v0.7.0, NATS binary mode since v0.3.0 (the release that added it).
For HTTP and Kafka the exposure of a message written by v0.1.0 to v0.6.1 depends on the reader: the v0.6.1 reader of `ce::v4` and v0.6.0 parse the body; the readers of `ce::v1` to `ce::v3` do not (see "Frozen generations").

### Not affected

- **Structured mode**: the payload is `data_base64` inside the document, and no media type decides how it is read.
- **MQTT 3.1.1** (`to_payload`, `from_payload`) and **`nats::to_payload`**: structured mode only.
- **The Protobuf entry points** (`to_message_protobuf` and the rest): the content type is `application/cloudevents+protobuf`, the body is the Protobuf event and never the data, and the reader does not read `datacontenttype` to decide a parse.
- **Every other payload alternative decoded from a document**: a `json_text` or `json_document` payload under a JSON media type is valid JSON by construction (the decoder parsed it), and `std::string` under a JSON media type is not produced by decode (`json_format` makes a string payload only under a media type that is not JSON). A caller can build a `json_text` or `std::string` payload with arbitrary text under a JSON media type by hand; that is the same exposure and it is outside the ruling (see question 6).

## Owner ruling

Ruled by the owner on 2026-11-09:

1. **Binary-mode `to_message` of the HTTP, Kafka and MQTT bindings refuses the event** with `errc::invalid_argument` and produces no message, when its `datacontenttype` is a JSON media type (one `is_json_content_type` accepts) and its payload is a `ce::binary` that is not valid JSON for the codec.
2. **The two alternatives were declined**: accepting it on read (keeping the body as binary, which changes `SWR-BIND-0008`) and leaving it as a known limitation.
3. **The harness carve-out is removed** once the refusal lands: the fuzz targets then check this refusal exactly as they check the one of `SWR-BIND-0019`.

The decisions that the ruling leaves open are analysed below and listed in "Open questions for the owner"; the draft requirement states the choice this request recommends, and the owner may overrule each.

## Analysis

### (a) Fix or break, by `D-BUILD-4` and `D-BUILD-5`

`D-BUILD-4` counts "a change to behaviour the published documentation states" as a break, and a break goes to a new generation with a minor version; a fix bumps the patch.
CR-0010 ruled the same kind of change "a defect fix" because the refused message never read back as the event sent.
Applying the same test here finds the answer less clear, for three reasons that CR-0010 did not have.

Evidence that it is a **break**:

- `SWR-HTTP-0008` (v0.1.0), `SWR-KAFKA-0002` (v0.2.0) and `SWR-MQTT-0009` (v0.7.0) state that binary mode writes the event's data as the body and its `datacontenttype` as the content type, and this request amends them again (after the exception CR-0010 added).
- `SWR-HTTP-0015` (v0.4.0) states that an event `from_message` returns re-encodes; an event decoded from a structured message and now refused in binary mode is a stated behaviour that changes. It is easier to reach than CR-0010's: any structured HTTP message with `data_base64` under `application/json` is one.
- **The message is valid for a reader that does not parse.** A CR-0010 message was ambiguous to every reader that follows the binding texts, because the content type declares structured mode. A binary-mode message with an opaque body under `application/json` is a valid message under the same texts: the body is the event data as is. The failure is the choice of this SDK's reader (`SWR-BIND-0008`, owner decision of 2026-09-28) to parse it. Whether the message reads back as the event sent depends on the receiver. This request makes the sender refuse a message that another SDK's reader, or this SDK's reader configured below, would take (the interop suite does not exercise the case, so this is stated from the binding texts, not measured).
- **A documented receiver configuration reads it back.** With `parse_binary_body = false` (`SWR-BIND-0012`, v0.6.1, in the guide) the body is kept as `json_text` unparsed and `from_message` succeeds, so a deployment that sends such events to a forwarder or a receiver configured this way works today and would get `invalid_argument` at the sender after the change.
- A caller that wrote such an event in binary mode got a message back before and gets `invalid_argument` now.

Evidence that it is a **fix**:

- The default reader of the same version loses the event: `from_message` returns `parse_error` for the bytes written, never the event sent. `SWR-BIND-0008` is `implemented` since v0.6.1 and the guide says so ("`from_message` fails with `parse_error` when a non-empty body under a JSON media type is not JSON"), so the documented read behaviour and the write that triggers it contradict each other, and the contradiction is in the SDK's own round trip, which is what the fuzz target of each binding checks.
- No document says that binary mode accepts binary data under a JSON media type, or shows it; `docs/GUIDE.md` and `README.md` show binary mode with `application/json` only for JSON payloads and `text/plain` for text.
- The v0.4.0 changelog lists a new refusal on the way out (ill-formed UTF-8) under "Fixed", and CR-0010 did the same.
- No declaration changes (`scripts/frozen_api_diff.py --base v0.7.0` is expected to pass, as for CR-0010).
- A caller who builds such an event deliberately, for a receiver that does not parse, can still send it: in structured mode, or under a media type that is not JSON (for example `application/octet-stream`).

The owner decides; this request neither rules nor assumes the answer of CR-0010 carries over.
The ruling has two branches, and the namespace, the release and the stage plan follow it (see "Versioning"):

- **Fix:** the refusal is a body-only change in `ce::v4` and ships as a v0.7.x patch, as CR-0010 did.
- **Break:** `D-BUILD-4` and `D-BUILD-5` put changed behaviour in a new generation, `ce::v5`, and keep `ce::v4` as it was published. The refusal is then not a change to `ce::v4`: `ce::v4` keeps writing the message, and the refusal lives in `ce::v5` with its own stages (the unchanged entities are brought into `ce::v5` as `D-BUILD-4` describes), and a minor release (v0.8.0).

The v0.7.0 changelog states MQTT binary mode writes a PUBLISH "whose Content Type property is `datacontenttype`" without exception, which is the statement the change would bend.

### (b) "Valid JSON for the codec" at write time, and its cost

The writer is not codec-free: `to_message<Codec>` is a template over the JSON codec in HTTP, Kafka, MQTT and NATS, and the `Codec` is already used to encode a structured event.
The refusal uses `Codec::parse(text_of(bytes))`, the call the reader makes (`binding::read_body<Codec>`), so "valid JSON for the codec" is the writer's codec accepting the bytes under its own parser limits (the nesting depth limit of `D-SEC-4`).
Two limits follow, and the CR states them rather than hides them:

- A receiver that uses another codec can accept what the writer's codec refuses and the reverse, in the edge cases where the codecs differ (duplicate member names, number ranges, depth). The writer cannot know the reader's codec; the refusal is "this codec would not read it back".
- `retain_document_up_to` and `parse_binary_body` are reader options (`json::decode_options`) and `to_message` takes no options. The refusal runs the parse with the default options.

Cost, by reading the code and not measured:

- The check runs only when the payload alternative is `ce::binary` and `is_json_content_type(datacontenttype)` is true. For every other event the added work is a `holds_alternative<ce::binary>` test, then (for a binary payload) one `ctre` match on the media type; the parse is reached only for a binary payload under a JSON media type, the case this request refuses or lets through.
- **The perf job has no timed binary-mode writer for Kafka, MQTT or NATS, and none for a `ce::binary` payload in HTTP.** `bench/perf/perf_probe.cpp::operations_for` registers one encode in binary mode, `http_encode_binary`, which writes a `json_text` payload (not a `ce::binary`) under `application/json`, so the check would not run for it. There is no `kafka_encode_binary`, `mqtt_encode_binary` or `nats_encode_binary`, and the probe includes `binding/http.hpp`, `binding/kafka.hpp` and `binding/nats.hpp` but not `binding/mqtt.hpp`. The only binary-mode writes of a `ce::binary` payload are in `body_message` (`application/octet-stream` and `text/plain`), which builds its message once in a static, outside the timed region. So **no timed operation exercises the new check, and the perf job as it stands cannot assess its cost**; an earlier draft of this request said otherwise and was wrong.
- **The implementing pull request adds the timed writer operations first** (see "Stage plan"), and the job then measures them against `main`. The probe is built against `main` as well as the pull request (the job measures `main` with the pull request's probe), so each new operation uses only declarations that exist on `main`, and it returns whether the write was attempted and not whether it succeeded: on `main` the write succeeds, on the pull request it may return the refusal.
- Where it does run, a payload that is JSON pays a full parse (a DOM built by the codec, discarded), once per write, in time and allocation proportional to the payload; the `json_codec` concept has no validate-only call, and adding one would change a published concept (a break for a custom codec), so the request does not propose it.
- `D-BIND-5` measured about 200 instructions of code generation cost on the receive path from a shared function, +2.2% to +2.5% on four Kafka operations against the +2% limit of `SWR-PERF-0001`, though the function itself was cheap. The write path gains a branch for the same reason. **The implementing pull request runs the perf job before it is opened, and a regression above the limit is reported to the owner** rather than assumed absent: this request records no measurement of the perf impact.

Order of refusals: an event whose media type starts with `application/cloudevents` (which includes `application/cloudevents+json`, a JSON media type) is refused by `SWR-BIND-0019` first, without parsing; this request applies to what remains.

### (c) The frozen generations `ce::v1` to `ce::v3`

By reading the readers, the frozen generations are **not exposed to the loss**: their `read_body` stores a body under a JSON media type as `json_text` without parsing it (`SWR-BIND-0008` records it: "In ce::v3 a binary-mode body under a JSON media type was stored as json_text without being parsed"), so a message written by a frozen writer reads back in a frozen reader as the same bytes in a `json_text`.
Their writers write the same message as `ce::v4`'s does today. What changes for them is only what a `ce::v4` reader does with it.
Following `D-BIND-5` and the CR-0010 default, **the frozen generations are left unchanged and documented**: a refusal there would remove a message that its own generation reads, and a frozen generation promised not to change.
A message written by a frozen writer and read by `ce::v4` still fails with `parse_error` for such bytes; that is the reader side of `SWR-BIND-0008` and is not changed.

### (d) The interplay with `parse_binary_body = false`

`parse_binary_body` is a reader option and the writer does not receive it.
With it set to false the reader keeps a JSON body unparsed and succeeds (`SWR-BIND-0012`), so the message the writer would now refuse is one that the opt-in reader accepts, as `json_text`, with its bytes unchanged.
The writer cannot know the reader's option; a refusal that depends on it would need a write-side option, which is a new declaration and which the owner has not asked for.
This request therefore states that **the refusal applies whatever the reader's option**: the write-time check is on the message as a default reader sees it, and a sender that targets an opt-in reader sends such an event in structured mode, or under a media type that is not JSON.
This is the most visible cost of the ruling and is listed as open question 3, with the alternative (an option on `to_message`, or no refusal) for the owner.

### (e) An empty payload

An empty `ce::binary` is not refused. `write_body` writes an empty body and the reader treats an empty body as no payload (`SWR-BIND-0010`), so the event reads back, with no payload instead of an empty `ce::binary` (as today).
A body of bytes that are only JSON whitespace is not empty and is not valid JSON, so it is refused.

### (f) The JSON media types

The set is what `is_json_content_type` accepts (`SWR-CORE-0024`): `*/json` and `*/*+json`, whatever the letter case, with parameters, and after leading whitespace (the grammar admits it).
The refusal calls the same function the reader calls, on the same value, so writer and reader cannot disagree about which media types parse. The refusal does not trim the media type: `is_json_content_type` already accepts the leading whitespace the media-type grammar admits, and an HTTP field parser that drops it leaves a JSON media type JSON.
A test holds the refusal to the reader for the same media types as `SWR-BIND-0019`'s suites do for the mode.

### (g) The other bindings and entry points

| binding or entry point | affected | why |
|---|---|---|
| HTTP binary mode | yes | measured |
| Kafka binary mode, `kafka::to_record` | yes | measured; `to_record` calls `to_message` |
| MQTT 5.0 binary mode, both name policies | yes | measured |
| MQTT 3.1.1 (`to_payload`) | no | structured only |
| NATS binary mode | **yes** | measured; not in the owner's ruling (question 1) |
| `nats::to_payload` | no | structured only |
| structured mode, all bindings | no | no media-type-dependent parse |
| Protobuf entry points | no | the body is the Protobuf event, not the data |

## Alternatives declined (owner ruling)

| alternative | why it was declined |
|---|---|
| Accept on read: keep a JSON-typed body that is not JSON as `ce::binary` | It changes `SWR-BIND-0008`, which the owner decided on 2026-09-28 (a malformed body under a JSON media type is a parse error, not stored). A reader could not tell a binary payload from a malformed JSON document. |
| Leave it as a known limitation | A caller sees the problem only when a consumer drops the message. It is the kind of loss CR-0010 removed for another case. |

## Requirements

A new requirement states the refusal, in the way `SWR-BIND-0019` does:

- **`SWR-BIND-0021` (new).** When the HTTP, Kafka or MQTT binding of `ce::v4` writes an event in binary mode, and the event's `datacontenttype` is a media type `is_json_content_type` accepts, and its payload is a non-empty `ce::binary` that the binding's codec does not parse as JSON, `to_message` shall return `errc::invalid_argument` and produce no message.

It is `reviewed`, with no `satisfied_by` and no `verified_by`, until the implementing pull request adds the code and the tests (the precedent of CR-0010 and CR-0005).
`SWR-BIND-0020` is not used here: it is reserved for CR-0012.

Four statements say that binary mode writes the data and the `datacontenttype` without exception or with the one exception of CR-0010, and each gains this one (`D-EXT-6`: a statement change bumps the version and returns an `implemented` or `approved` requirement to `approved` without `delivered_in`; the `approved` ones below stay `approved`):

| requirement | version | the amendment |
|---|---|---|
| `SWR-HTTP-0008` | 2 to 3 | the `Content-Type` mapping holds for an event neither `SWR-BIND-0019` nor `SWR-BIND-0021` refuses |
| `SWR-HTTP-0015` | 3 to 4 | an event that `to_message` refuses only by `SWR-BIND-0019` or `SWR-BIND-0021` is not an error of `from_message` |
| `SWR-KAFKA-0002` | 2 to 3 | the `content-type` mapping holds for an event neither requirement refuses |
| `SWR-MQTT-0009` | 2 to 3 | the Content Type mapping holds for an event neither requirement refuses |

These amendments start from the versions on `main`, which include CR-0010 and `SWR-BIND-0019`.
`SWR-BIND-0008` and `SWR-BIND-0012` are not amended: the readers do not change, and both are listed in `impacts` because the refusal is the write-side half of the first and refuses what the second accepts (question 3).
`SWR-HTTP-0003` (`to_message` returns a message in the mode asked for) already admits a refusal, as `SWR-BIND-0019` noted.
`SWR-SEC-0001` (the fuzz targets) is not amended; its targets lose the carve-out below.

## Frozen generations

See (c): unchanged and documented, with no exposure to the loss within their own generation. Whether they should refuse anyway, to keep the three generations alike, is question 5.

## Rule 4 and the API

This section is the **fix** branch (see "Versioning"). Under the **break** branch the same helper and calls are added to the `ce::v5` copies of the three bindings, and `ce::v4` is not touched.
The change changes function bodies of `ce::v4` and adds declarations only:

- a `binding::detail` helper, template over the codec, that returns the refusal for a `ce::binary` payload under a JSON media type that the codec does not parse;
- the call to it in the binary-mode `to_message` of HTTP, Kafka and MQTT (and NATS if question 1 is answered that way).

No declaration is removed or changed, and no reader changes. A `ce::v1` to `ce::v3` header is not touched.

## Stage plan

**Fix branch.** One implementing pull request, after CR-0010's lands. **Break branch:** the same work in two stages, first the `ce::v5` generation (see "Versioning"), then the work below in `ce::v5`; the changelog entry is then under "Breaking" and the release is v0.8.0.
The pull request carries: the timed writer operations in `bench/perf/perf_probe.cpp` (added first, as a commit that compiles and measures on `main`: `kafka_encode_binary_json_binary`, `mqtt_encode_binary_json_binary`, `nats_encode_binary_json_binary`, `http_encode_binary_json_binary` for a `ce::binary` payload that is valid JSON under `application/json` (the full parse), and the same four with bytes that are not JSON (the refusal path), plus a `ce::binary` under `application/octet-stream` for the three bindings whose binary-mode write has no timed case; and, to price the extension of question 6, timed `json_text` writers (a valid `json_text` under `application/json`, as `bench::full_event()` carries) for Kafka, MQTT (both name policies) and NATS, beside the existing `http_encode_binary`, because the `ce::binary` operations cannot measure what validating a `json_text` would add; the MQTT cases need `binding/mqtt.hpp` in the probe and use both name policies), the helper and the three writers, the suites above, the seed assertions, the removal of the harness carve-out (`ce_fuzz::binary_under_json` and its use in `check_binary_write`), a changelog entry under "Fixed" that replaces the "Known limitations" entry of v0.7.1 and names every affected binding, **NATS included** (the entry already names HTTP, Kafka, MQTT and NATS; whether the refusal covers it is question 1: if it does not, the entry says so and keeps NATS as a known limitation), a note in the guide's HTTP, Kafka and MQTT sections and in "Forwarding a binary-mode message without parsing it", a `D-BIND` entry, the perf job run, and the passing of `scripts/frozen_api_diff.py`.
The release proposal depends on question 4 and on the owner's later ruling: v0.7.1 if a fix, a minor if a break.

## Open questions for the owner

Each is a decision the request does not take; the draft requirement and the plan state the default named.

1. **NATS.** The probe shows binary data under a JSON media type loses the event in NATS binary mode too (the media type travels as `ce-datacontenttype` but the reader parses all the same). The ruling names HTTP, Kafka and MQTT. Default in this draft: the requirement covers the three as ruled, and NATS is pinned by a test as unchanged until the owner rules; the recommendation is to include NATS, which adds one call and one suite and makes the four bindings alike.
2. **Where the refusal names its cause.** `SWR-BIND-0019` names `datacontenttype` in `where`. Here the media type alone is valid (it carries any payload that is JSON) and the payload alone is valid (it carries under another media type), so the cause is the pair. Default in this draft: `where` is `data`, which also lets the fuzz harness tell the two refusals apart without a second error code (the MQTT transport-limit refusal names an attribute and never `data` or `datacontenttype`, which `is_transport_refusal` relies on). The alternative is `datacontenttype`, as CR-0010 does.
3. **The reader's `parse_binary_body = false`.** The refusal applies whatever the reader's option, because the writer does not know it (analysis (d)). It refuses a message that an opt-in reader would accept. Alternatives: an option on `to_message` (a new declaration), or no refusal for this binding. Default: refuse always.
4. **Fix or break (release number).** See (a). The evidence differs from CR-0010: the message is valid to a reader that does not parse, and a documented receiver option reads it back.
5. **The frozen generations.** Default: unchanged and documented, because they read the message they write (analysis (c)).
6. **Payloads built by hand.** A `json_text` or `std::string` payload with invalid JSON under a JSON media type has the same exposure and is not produced by decode. Default: the requirement says `ce::binary` only, as ruled; the alternative is any payload that is not already known to be JSON, which makes the writer parse a `std::string` too.
   A caller need not build such a payload by hand, though: `binding::read_body` returns a `json_text` that is not valid JSON when the reader is configured with `parse_binary_body = false` (`SWR-BIND-0012`), and a forwarder that decodes with the option off and then writes the event in binary mode (a relay is the intended use of the option) writes that `json_text` under a JSON media type. A default reader downstream then fails with `parse_error`, exactly the loss of this request, and the `ce::binary`-only check skips the event, so the forwarding path that motivated `parse_binary_body = false` is left unprotected.
   Structured mode is not an escape for that payload: `json_format::encode_data` parses a `json_text` (`Codec::parse(held.raw)`) and returns `parse_error` for malformed text (`test/json_format_test.cpp`), so structured encoding refuses it locally instead of forwarding it. The relay forwards those bytes in structured mode only after converting the payload to `ce::binary`, which is then encoded as `data_base64`.
   The sub-questions for the owner: (i) whether the check extends to a `json_text` payload (and a `std::string`) that is not valid JSON; (ii) what the writer knows: a `json_text` produced by a decode is valid JSON by construction in the default configuration, and unknown only when the option was off, but the payload type does not say which, so the writer would have to parse every `json_text` it writes in binary mode under a JSON media type, including the valid ones (the common case: `bench::full_event()` is one); (iii) the cost: a parse per write for every JSON event, which is the hot path, against a parse only for `ce::binary` as drafted, to be measured by the operations in "Stage plan" before the owner rules, and (iv) the alternative that costs nothing on the write path: a guide note in "Forwarding a binary-mode message without parsing it" (which does not say it today) that an event decoded with the option off holds unvalidated bytes, and a relay that re-encodes it in binary mode under a JSON media type can write a message that a default reader refuses; the note says to check the bytes first, or to convert the payload to `ce::binary` before encoding (structured mode does not forward malformed `json_text`: `json_format::encode_data` parses it and returns `parse_error`, so structured encoding is a local refusal, not a forward; only a `ce::binary` payload travels as `data_base64`), and the limitation is recorded as one of the opt-in.
   Proposal, not a decision: keep the requirement at `ce::binary` as ruled, add the note of (iv) to the guide in the implementing pull request, and decide (i) after the perf operations show what a parse per `json_text` write costs; if it is within the +2% of `SWR-PERF-0001` on the `json_text` writer operations (not the `ce::binary` ones, which parse under the drafted requirement already), extend the check, otherwise leave it as documented.
7. **Validation cost and the codec's reach.** The implementing pull request measures the perf job and reports it; the owner decides whether a regression above +2% (`SWR-PERF-0001`) is accepted, or the check moves behind a validate-only call on the codec concept (a change to a published concept, which this request does not propose).
