# CR-0012: A datacontenttype containing CR or LF is invalid

> **Status, 2026-11-10.** Approved: the owner ruled the rule, its scope and its versioning on 2026-11-10 (see "Owner ruling").
> No question is open.

## What prompted this

The review of the CR-0010 fix (pull request #133) found on 2026-11-09 that a `datacontenttype` such as `"\r\ntext/plain"` is a valid value.
Binary mode writes `datacontenttype` into the content-type field as it is, so the line break reaches the HTTP `Content-Type` header.
An HTTP adapter that writes header values without checking them would emit a broken header, or a second header of the sender's choosing.
CR-0010 recorded the observation and the owner gave it this change request.

## The defect

The media-type grammar every `datacontenttype` is checked against is `content_type_pattern`, `^\s*type/subtype\s*(;.*)?$`, in `include/cloudevents/attributes.hpp` (`ce::v2::detail`, shared by `ce::v2`, `ce::v3` and `ce::v4`), with a byte-identical copy in `include/cloudevents/v1/core.hpp`.
It admits CR and LF in three places:

1. the `\s*` before the type: `"\r\ntext/plain"`;
2. the `\s*` after the subtype: `"text/plain\r\n"`;
3. the parameter part `;.*`, which admits any byte: `"text/plain; a=b\r\nX-Injected: 1"`.

The third is the full header-injection shape.
The same text without the `;` (`"text/plain\r\nX-Injected: 1"`) is refused only because the grammar happens not to match it, so trimming leading whitespace would not close the defect.

### Evidence, before the fix

Measured on `main` at `0184527` (after CR-0010), g++-16, `-std=c++20`, nlohmann codec.
"raw CR/LF" means the value written into the field contains the bytes CR or LF.

| `datacontenttype` | `make` | v1 `validate` | JSON decode | HTTP binary | Kafka binary | MQTT binary | NATS binary |
|---|---|---|---|---|---|---|---|
| `\r\ntext/plain`, `\ntext/plain` | accepted | accepted | decodes | raw CR/LF in `Content-Type` | raw CR/LF in `content-type` | raw CR/LF in Content Type | `%0D%0A` in `ce-datacontenttype` |
| `text/plain\r\n`, `text/plain\r` | accepted | accepted | decodes | raw CR/LF | raw CR/LF | raw CR/LF | percent-encoded |
| `text/plain; a=b\r\nX-Injected: 1` | accepted | accepted | decodes | raw CR/LF | raw CR/LF | raw CR/LF | percent-encoded |
| `text/plain\r\nX-Injected: 1`, `text\r\n/plain` | `invalid_content_type` | refused | `invalid_content_type` | - | - | - | - |
| ` text/plain`, `text/plain \t` (control) | accepted | accepted | decodes | written as is | as is | as is | percent-encoded |

- A decoded JSON document re-emits the raw CR/LF through HTTP binary mode.
- Structured mode escapes the characters inside the JSON string, so it is safe on the wire.
- NATS percent-encodes the value, and its reader decodes `%0D%0A` back into CR LF, so a NATS message carries such an event too.
- Only HTTP is a framing hazard: a Kafka header value is bytes and an MQTT Content Type property is a length-prefixed string.
  Both carry the line break to a consumer that may copy it into a header of its own.
- The HTTP binary writers of `ce::v1`, `ce::v2` and `ce::v3` write the parameter case with raw CR/LF as well.

Exposure by release: the pattern is unchanged since the first commit of the attribute validation, so every release from v0.1.0 to v0.7.0 accepts such a value.

## Owner ruling

Ruled by the owner on 2026-11-10:

1. **The core rule.** A `datacontenttype` that contains CR (U+000D) or LF (U+000A) anywhere, the parameter part included, is invalid.
   The check refuses it with `errc::invalid_content_type`, the code a malformed media type already returns, naming `datacontenttype`.
   It is added to the body of `ce::v2::detail::datacontenttype_policy::check`, so `datacontenttype::make`, the `_mediatype` literal, JSON and Protobuf decoding and every binding's reader refuse it in `ce::v2`, `ce::v3` and `ce::v4`.
   `content_type_pattern` and every other declaration stay as they are.
2. **The writer refusal, as defence in depth.** The binary-mode `to_message` of the HTTP, Kafka and MQTT bindings of `ce::v4` refuses a `datacontenttype` containing CR or LF with `errc::invalid_argument` naming `datacontenttype`, next to the CR-0010 refusal.
   It guards the content-type field against a value that did not go through the validated attribute.
   While the core rule holds, no event reaches it; both stay.
3. **`ce::v1`** takes the same check in the body of `ce::v1::event::validate()`, because a body-only change passes the frozen-API gate and the `ce::v1` suites.
4. **Spaces and tabs before or after the media type stay accepted.** RFC 9110 allows them around a field value and an HTTP field parser drops them; only CR and LF are refused.
5. **A defect fix, released as v0.7.1** (see "Versioning").
6. **One pull request** carries the rule, the writer refusal, the tests, the fuzz checks and the seeds.

## Why CR and LF, and only they

The CloudEvents core specification makes `datacontenttype` a media type as RFC 2046 defines it: a type, a subtype and parameters.
Optional whitespace belongs to the field that carries a value, not to the media type, and RFC 9110 (section 5.5) forbids CR and LF in a field value.
A parameter value may be a quoted string, and RFC 9110's `qdtext` excludes CR and LF too, so no valid media type contains either.
Space and tab are legal optional whitespace around a field value and inside a quoted parameter, and refusing them would refuse values that are valid today and harmless.
VT and FF are not refused: they are not line breaks in any of the four transports and the owner did not rule on them.

## Alternatives declined

| alternative | why it was declined |
|---|---|
| Sanitise in the HTTP writer only | It leaves Kafka and MQTT, whose consumers may copy the value into a header, and it leaves an invalid value in a valid event, decoded from JSON or Protobuf and passed on. |
| Strip CR and LF instead of refusing | It changes the event silently: the receiver gets a `datacontenttype` the sender did not send, and a stripped `"text/plain; a=b\r\nX: 1"` becomes a different parameter list. |
| Document it only | A caller cannot check every value it forwards, and the library already validates this attribute; the check belongs where the grammar is. |
| Change `content_type_pattern` | Its type is `ctll::fixed_string<N>`, which changes with the pattern's length, so the frozen-API gate fails; it also drives `is_json_content_type` (SWR-CORE-0024), which is a separate question. |
| A `ce::v4`-only core rule | `ce::v4::datacontenttype` is `ce::v2::datacontenttype`; a separate type for `ce::v4` changes a published declaration. |

## Requirements

No requirement states the media-type grammar today: `SWR-CORE-0026` makes `datacontenttype` a type that cannot hold a forbidden value, and `SWR-CORE-0019` refuses an empty one.
The rule is therefore a new requirement in the core family rather than an amendment.

- **`SWR-CORE-0041` (new).** When the text offered for a `datacontenttype` contains CR or LF anywhere, the check behind its factory and its literal shall refuse it with `errc::invalid_content_type` naming `datacontenttype`, in `ce::v1` (`event::validate`) as in `ce::v2` to `ce::v4`; space and tab before or after the media type stay accepted.
- **`SWR-BIND-0020` (new).** When the HTTP, Kafka or MQTT binding of `ce::v4` writes an event in binary mode, it shall check the `datacontenttype` it would write into the content-type field and return `errc::invalid_argument` naming `datacontenttype`, producing no message, when the value contains CR or LF.

No statement is amended.
`SWR-HTTP-0008`, `SWR-KAFKA-0002` and `SWR-MQTT-0009` state the content-type mapping for an event that neither `SWR-BIND-0019` nor `SWR-BIND-0021` (CR-0011) refuses; `SWR-BIND-0020` refuses no value an event can hold under `SWR-CORE-0041`, so the mappings stay exact.
`SWR-SEC-0001` (the fuzz targets) is listed because its targets gain a check below.

Each gains seeds with CR or LF at the start, at the end and in the parameter part.

## Versioning

`D-BUILD-4` counts "a change to behaviour the published documentation states" as a break, and a break goes to a new generation with a minor version.
The evidence for both readings is kept below.

**Owner decision, 2026-11-10: a defect fix, not a break.** An RFC 2046 media type cannot contain CR or LF, and RFC 9110 field values forbid them, so the refused values were never valid `datacontenttype`s. The owner ruled CR-0010 a defect fix on the same grounds. The release is v0.7.1, a patch (D-BUILD-5), with no new generation.

Evidence that it is a **break**:

- The change is in the shared core validation of `ce::v2`, `ce::v3` and `ce::v4`, which v0.4.0, v0.5.0 and v0.6.0 published, and in `ce::v1::event::validate()`, which v0.3.0 published.
- A JSON or Protobuf document, or an HTTP, Kafka, MQTT or NATS message, whose `datacontenttype` contains CR or LF decoded before and fails with `invalid_content_type` now, in every generation that has that format or binding (Protobuf and MQTT exist in `ce::v4` only).
- `datacontenttype::make` returned a value for such text and returns `invalid_content_type` now.
- `D-BIND-5` left the frozen generations' binary writers alone; this change reaches them through the shared check.

Evidence that it is a **fix**:

- The CloudEvents core specification makes `datacontenttype` an RFC 2046 media type, which has no place for CR or LF.
  The guide documents the attribute as "an RFC 2046 media type" and `invalid_content_type` as "a `datacontenttype` that is not a media type", so the published documentation already excludes these values.
- No document, test or example names such a value as valid; the guide's examples are `application/json`, `text/plain`, `image/png`, `application/protobuf` and the CloudEvents media types.
- The accepted values could only be written into a header field that may not contain them (RFC 9110, 5.5).
- No declaration changes: `scripts/frozen_api_diff.py --base v0.7.0` passes.

## Rule 4 and the API

The change edits function bodies in `ce::v1` and `ce::v2` and adds to `ce::v4::binding::detail`:

- the body of `ce::v2::detail::datacontenttype_policy::check` and of `ce::v1::event::validate()`;
- `binding::detail::refuse_media_type`, the string check the binary writers call (through `refuse_format_media_type`, from CR-0010 and not yet released), and the named set of line-break characters it tests.

No declaration is removed or changed.

## Acceptance

The implementing pull request carries the two requirements, the suites above, the fuzz checks and seeds, a changelog entry under "Fixed", a note in the guide and a `D-CORE` entry, and passes the frozen-API gate against v0.7.0.
